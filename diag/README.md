# diag —— 现场诊断脚本

这些脚本不是应用的一部分，是排查「隧道卡顿 / 传不动 / 连接建不起来」时用的探针。
`CHANGELOG.md` 里 v0.12.x ~ v0.13.x 那些实测数字，就是它们量出来的。

大多数脚本假设**本机已经跑着 Stronghold Link，而且本机是加入者**
（也就是 `127.0.0.1:3000` 由它监听）；`pool-verify.cjs` 例外，它自己会把
房主 + 加入者都在本机拉起来。

| 脚本 | 干什么 |
| --- | --- |
| `pool-verify.cjs` | 在**真实 Steam P2P** 上做预热连接池的 A/B —— 单元测试用的是假 SDK，握手瞬间完成，量不出"排队限速"。用法 `node diag\pool-verify.cjs [池子条数] [测几条]`；`SHL_STEAM_POOL=0` 是基线；第 2 个参数给 `0` 则只盯池子、不打扰它 |
| `latency.cjs` | 连 N 次量首字节延迟（第一次含握手） |
| `page-load.cjs` | 把首页资源整页拉一遍：总字节数、总耗时、每条资源的速度 |
| `range-one.cjs` | 一个进程只发一个 Range 请求（= 一条全新连接），用来分辨"断"是跟文件大小有关，还是跟新建连接是否成功有关 |
| `range-scan.cjs` | 连续分段下载，找断点到底落在哪个字节数 |
| `wall-discriminate.cjs` | 判别"慢读被切断"还是"超时"：故意放慢读速，看断点是否还是同一个字节数 |
| `tunnel-check.cjs` | 隧道体检（监听端口、连接数、字节数） |
| `bump-version.cjs` | 发版时同步版本号：`node diag\bump-version.cjs <旧版本> <新版本>` |

## `pool-verify.cjs` 的几个开关

这个脚本是排查"每条新连接都要重新握手"那条主线时最常用的一个，所以单独说。

- 它自己起一个**真的 `node:http` 替身**当游戏服务（`headersTimeout=60000`、
  `keepAliveTimeout=5000`），因为池子里的连接"连上但一句话不说"，踩的是
  `headersTimeout` 而不是有响应之后的 `keepAliveTimeout` —— 拿裸 `net` 冒充量不准。
- `SHL_PROBE_HTTP`：`1.0`（默认）让服务端**回完响应就关**本地连接，正是现场游戏服务的
  行为；`1.1` 切到 keep-alive 做对照。v0.13.3 那个"最后一段字节被丢掉"的 bug 就是靠
  这两个值一比一对照揪出来的（同代码同分钟：`1.1` 3/3 通过、`1.0` 4/4 全部 40 秒超时）。
- `SHL_PROBE_DELAY_MS`：连上之后先等 N 毫秒再发请求，用来分辨"刚交接那一刻发数据会丢"
  和"这条链路根本发不出去"。
- `SHL_BIG_BYTES` + `SHL_PROBE_PATH=/big` + `SHL_PROBE_WANT=<字节数>`：让替身吐一大坨
  （默认 512 KiB）并要求收满，用来验证"大响应还在路上、服务端就把本地连接关了"
  这条路径会不会被截断。
- 收尾时会打印房主与加入者各自最后两条 `peer-stats`，每条连接都带 `queue`
  （此刻还压在 `peer.out` 里没发出去的字节数）。

每个脚本顶部的注释里都写了完整用法，以及「输出里该认哪几个数」。
