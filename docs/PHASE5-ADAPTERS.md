# 第五阶段：游戏适配器系统与连接方式（v0.8.0）

## 1. 这一阶段解决什么问题

前四个阶段里，工具只有一条隐含假设：**「房主要开放端口，加入者把客户端指向本机入口」**。
但真实游戏差别很大：

| 游戏类型 | 正确的联机方式 | 老版本是否好用 |
| --- | --- | --- |
| 原生 TCP/UDP 端口的游戏 | 房主开放中继端口 → 加入者客户端连本机入口 | ✅ |
| **浏览器游戏**（先开网页、网页再连 WebSocket，同端口） | 加入者**不用装游戏服务**，浏览器打开本机入口端口，页面与 WebSocket 一起经隧道到房主 | ❌ 说明里没写，玩家会卡在「我该打开哪个地址」 |
| 同一局域网 | 其实不需要中继，只要把地址说清楚 | ❌ 硬套中继流程反而更麻烦 |
| 跨网络 + 有 Steam | Steam P2P 隧道，不需要端口转发 | ⚠️ 有适配器但界面把字段和端口规则混在一起 |

因此本阶段把这些差异收敛成**连接方式（recipe）**：每种游戏一套「要填什么 + 两端怎么连」的完整配方，
界面按配方切换字段，邀请信息里直接带上「加入者怎么做」。

## 2. 新增文件

| 文件 | 作用 |
| --- | --- |
| `network/adapters.cjs` | 适配器与配方注册表：四种配方、字段声明、启动参数组装、两端连接说明（纯函数，易测） |
| `test/adapters.test.cjs`（7 例） | 配方清单、Steam 可用性标记、适配器状态映射、启动参数组装与校验、连接说明文案 |

配套改动：

- `session.cjs`：新增 `adapter: 'none'`（**不做转发**，0 条通道，安全信息明确写「未建立任何隧道」）；
  本地/Steam 房主的邀请信息里带上 `hints`（加入者怎么做），`inviteText()` 按适配器类型分别渲染。
- `main.cjs`：`adapters:list` 改为由注册表生成；新增 `adapters:recipes` 与 `adapters:recipe-hints`；
  配置持久化新增 `recipe` 字段。
- `preload.cjs`：暴露 `adapters.recipes()` 与 `adapters.recipeHints(input)`。
- 界面：**连接方式**下拉（取代原来「传输适配器」的裸选择），按配方切换字段、显示配方摘要与实时连接说明；
  配置编辑器里可以为每个游戏保存连接方式。

## 3. 四种连接方式

| id | 名称 | 适配器 | 需要填 | 加入者怎么连 |
| --- | --- | --- | --- | --- |
| `local-ports` | 本地中继（TCP / UDP 端口规则） | local | 端口规则、监听地址、口令 | 游戏客户端连 `127.0.0.1:<本地入口>` |
| `local-web` | 本地中继 + 浏览器游戏 | local | 同上 | **浏览器打开 `http://127.0.0.1:<本机入口>`**（页面与 WS 都经隧道）；也可直连 `http://<房主IP>:<中继端口>` |
| `steam-tunnel` | Steam P2P 隧道 | steam | 本地游戏端口、AppID、房主 SteamID | 填房主 SteamID 后启动；不需要端口转发 |
| `lan-direct` | 不做中继（局域网直连） | none | 游戏端口 | 直接打开 `http://<房主IP>:<游戏端口>`；**工具不转发任何流量** |

`lan-direct` 是刻意保留的诚实选项：同一局域网时中继纯属多余，与其让用户绕一圈，不如明确告诉他「这次没有隧道」。

## 4. 默认配置已换成真实游戏

原来默认配置里的示例是「Stronghold Link / 经典城堡策略游戏配置示例」，与实际项目无关。现在第一条默认配置是：

```
名称：卫戍协议：盟约
连接方式：local-web（本地中继 + 浏览器游戏）
端口规则：TCP,3000,3001   （本地游戏 3000，对好友开放 3001）
说明：明日方舟「卫戍协议：盟约」同人联机（1–4 人）。加入者浏览器打开 http://127.0.0.1:3000，
      页面与 WebSocket 都经隧道到房主，加入者不需要在自己机器上跑游戏服务。
```

另外两条示例改成「通用 TCP 游戏（示例）」「通用 UDP 游戏（示例）」，并各自带合适的默认连接方式。
配置编辑器新增「连接方式」下拉，会随配置一起持久化（`profiles:save` 校验并保留 `recipe`）。

> 为什么这样对：该游戏的客户端 WebSocket 地址等于页面来源，所以只要加入者的页面来自本机入口端口，
> 页面请求与 `/ws` 都会走同一条隧道——不需要给游戏打补丁，也不需要 Deferred 的端口改写。

## 6. 怎么用（卫戍协议：盟约 为例）

**局域网 / 已有 VPN**

- 房主：游戏库选「卫戍协议：盟约」→ 会话 → 连接方式保持 **本地中继 + 浏览器游戏** → 角色 房主 → 启动桥接 → 复制邀请信息。
- 加入者：粘贴邀请码 → 启动桥接 → **浏览器打开 `http://127.0.0.1:3000`**，进入游戏即可。
  （加入者不需要安装/运行游戏服务；页面与 WebSocket 都从房主那边来。）
- 如果两人本来就在同一局域网，也可以直接选「不做中继（局域网直连）」，让好友打开 `http://<房主IP>:3000`。

**跨网络（无公网端口）**

- 有 Steamworks SDK：连接方式选 **Steam P2P 隧道**（见 [PHASE4-STEAM.md](PHASE4-STEAM.md)）。
- 没有 SDK：仍需要端口映射 / VPN，工具不会假装能穿透 NAT。

## 7. 已知限制

1. **一条配方=一种假设**：如果某个游戏需要在同一次会话里同时做「端口转发 + 浏览器隧道」（例如页面在 3000、WS 在 3001），请用多行端口规则，并在说明里写清两个地址。
2. **`local-web` 依赖游戏客户端使用「页面同源」的 WebSocket**。若某游戏把 WS 地址写死在别的端口，需要额外规则或（阶段 4 思路的）注入式适配器。
3. **加入者浏览器缓存**：隧道断开后浏览器里仍是旧页面，需要刷新；这一点写在邀请说明里。
4. **仍未实测**：跨设备（两台电脑）、真实 Steam P2P。本环境只有一台机器且缺 Steamworks SDK。
