## 0. 先说三条会改变方案的硬约束

审计过程中发现的、规格里**假设错了**的三件事。它们直接决定方案怎么做：

### 0.1 仓库里没有 `steamworks.js`

规格 §五 说「必须根据当前 `steamworks.js` 的真实 binding 查找正确 API」。实际上：

- 唯一的 Steam 绑定是 **`steamworks-ffi-node@0.11.3`**（`source/package.json:27`，在 `optionalDependencies` 里）。
- 它是 **koffi FFI** 包，不是 `.node` 原生插件。`node_modules/steamworks-ffi-node/package.json:5` `"main": "dist/index.js"`、`:6` `"types": "dist/index.d.ts"`、`:70` `"koffi": "^3.1.5"`。
- `prebuilds/` 里只有覆盖层 `steam-overlay.node`；网络能力全部走 koffi 对 `steam_api64.dll` 做**运行时动态绑定**。

**影响**：所有 API 存在性都必须查 `dist/index.d.ts` 的真实导出，不能凭 `steamworks.js` 的记忆写。好消息是规格点名的 API **基本都在**（见 0.2）。

### 0.3 两个必须绕过的坑

**(a) 通过 binding 配置只能走 Global scope —— 但 DLL 里其实有按连接配的符号。**

`connectP2P(remoteSteamId, virtualPort?)` 的实现**硬编码 `nOptions=0`**（`dist/internal/SteamNetworkingSocketsManager.js:331`），没有地方传 `SteamNetworkingConfigValue_t[]`。`steam-netconfig.cjs:18-21` 里就是这么记的。

但直接扫 `steamworks_sdk/redistributable_bin/win64/steam_api64.dll` 的导出表（31 个候选名）结果是：

| 结果 | 符号 |
|---|---|
| **DLL 里有，binding 没声明（可用 koffi 逃生口补）** | `SetConnectionConfigValueInt32`、`SetGlobalConfigValueInt32/Float/String/Ptr`、`SetConfigValue`、`GetConfigValue`、`GetConfigValueInfo`、`IterateGenericEditableConfigValues`、`CreateListenSocketIP`、`SetGlobalCallback_SteamNetConnectionStatusChanged` |
| **DLL 里也没有（彻底做不到）** | `ConnectP2PRelay`、`GetQuickConnectionStatus`、`SetConnectionRealTimeStatusCallback` |

⇒ 结论修正：全局配置**已经够用且已集中**（`network/steam-netconfig.cjs`，见 A.6），本方案**不引入按连接配置**。但「按连接配」在 DLL 层面是**可补的**，留档备查 —— 如果将来真的需要给某条干道单独放宽 `timeoutInitial`，不必去改 binding 源码，走 `steam-netconfig.cjs` 已有的 koffi 逃生口加一个符号即可。

**(b) 写配置靠 koffi 逃生口，改名会静默失效。**
`steamworks-ffi-node` 的 JS 层**没有** `setConfigValue`。项目自己在 `network/steam-netconfig.cjs:402` 拿 `loader.getLibrary()`，`:411` 动态取符号：

```js
lib.func('SteamAPI_ISteamNetworkingUtils_SetGlobalConfigValueInt32','bool',['void*','int','int'])
```

`:423` 回落 `..._SetConfigValue`，`:434` `..._GetConfigValue`。挂载点 `dist/internal/SteamLibraryLoader.js:858 getLibrary()`。
踩过的原始报错：`Cannot find function 'SteamAPI_ISteamNetworkingUtils_SetConfigValueInt32' in shared library` —— PE 导出表 1078 个符号里确实没有。
**任何「整理配置代码」的改动都必须保持这条链路原样，否则只会静默变成「配置没下发」而不是报错。**（`applyNetConfig` 的纪律就是「设一个读回校验一个、缺符号降级不抛」，`steam-netconfig.cjs:23-27`。）

**(c) 状态回调不是事件发射器。** 没有 `steam.on()`。只有三层混合：
- native 全局回调 `SetGlobalCallback_SteamNetConnectionStatusChanged`（`dist/internal/SteamLibraryLoader.js:438`，注册于 `SteamNetworkingSocketsManager.js:142`）
- JS 订阅 `ns.onConnectionStateChange(handler)`（`d.ts:408`，**返回反注册函数**）
- 轮询兜底 `getPendingStateChanges()`（`d.ts:421`）/ `getPendingConnectionRequests()`（`d.ts:445`）

项目用的是 `onConnectionStateChange`（`steam-adapter.cjs:1120` 房主、`:1959` 加入者）+ 防御性 `pollConnectionStates()`/`ensureCallbackRegistered()`（`:198-199`）。

### D. retry storm / pool churn 的根源

分四层，逐层都能在代码里指出来：

**D.1 需求侧：一次页面加载要 6~25 条连接。**
现场 12 分钟会话账本：`本机连接进来` 命中池子 53 次 / 临时握手 **62 次**（命中率仅 46%）。
⇒ 单位时间要消耗 100+ 条 P2P 连接。

**D.2 供给侧：池子**结构上**填不满。**
`refillPool :1760-1776` 是**串行递归**：

```js
const created = spawnWarmPeer();     // :1770  一次只开一条
...
refillPool();                        // :1774  开完再开下一条
```

一次只开一条，而**每条握手要 11~36 秒**（现场实测分布：11s×1、16s×1、22s×1、24s×1、27s×1、29s×1、**30s×11**、31s×1、35s×1、36s×1）。`PEER_POOL_TARGET = 4`（`:315`）要填满理论上就要 2 分钟以上。
⇒ **增速永远追不上消耗。** 现场 `隧道存量 4 条 ｜ 预热池 备用4/4 累计开83 就绪67 命中52 未命中57 换新12 自死15 均寿31s`。

**D.3 寿命侧：池子连接活不过被用上。**
`:1653` `idleMs = round(45000 × (0.6~0.9))` = **27~40.5 秒**。
理由（注释 `:1643-1650`）：房主那边每条连接都对应一个到游戏端口的本机 socket，游戏服务器 ~60 秒（Node `headersTimeout`）会把「一句话没说」的连接关掉。
⇒ 预热连接的实际寿命 ≈ 一次握手的时间。**这是 0.13.3 架构下的必然，不是参数没调好。**

**D.4 放大侧：失败还会再压三次。**
`:1696` 条件成立时 `schedulePeerReconnect`（`:1301`），`PEER_RECONNECT_MAX = 3`（`:286`）、`PEER_RECONNECT_DELAY_MS = 150`（`:287`）。
⇒ 一次浏览器连接最坏能变成 4 次握手尝试。

**D.5 为什么「relay 档位」是头号嫌疑（现场证据）。**
校园网期间：`新增 P2P 连接几乎 100% 失败`（5003×27 / 5008 / 4001），但**已建立的长连接仍能存活**；同机回环 P2P 也失败。
Steam 客户端自身同期被掐：`ConnectionDisconnected('I/O Operation Failed')` 20:52:41 / 20:53:48 / 20:54:46 / 20:55:31，`StartAutoReconnect` 日志里共 170 次，`failed talking to cm` **1708** 次。
`relay` 档把 `iceEnable` 设成 `ICE_DISABLED(0)`，等于**放弃所有直连路径，全部押在 SDR 中继的 rendezvous 上** —— 而 rendezvous 恰恰是故障期间最先坏的那一环。
⇒ **规格 §二十二 说「不要把 `iceEnable = 0` 硬编码到所有场景」，这条完全成立。** 现在的默认档是 `ice`（不是 `relay`），但用户 UI 上如果切到 `relay`，就会踩中这个。

**D.6 结论：把 Steam rendezvous failure 放大成了大量业务 TCP failure。**
这正是规格 §二 末尾那句话。**根治办法只有一个：让业务连接数量不再决定 Steam P2P 连接数量。**

## Phase 2 — 网络架构方案

### 2.0 三层解耦：本方案的全部要点就是这一张图

规格 §十五 的核心要求是「SteamConnection / Session / Stream 三层分离」，§三十七 的验收是「P2P 数量与 Minecraft TCP 数量无关」。落地成四层，**依赖只能从上往下，不能从下往上**：

```
业务层    本机 TCP（浏览器 / 游戏客户端）        N 条，任意多，1 ≤ N ≤ 数百
          └ 一一对应 ▼
Stream 层 MuxStream                              N 条，与业务 TCP 一一对应
          └ N 条 stream 共享 ▼
Session 层 MuxSession                            1 个远端玩家 = 1 个 Session
          └ Session 绑定 1~2 条 ▼
传输层    SteamConnection（Primary + 可选 Backup） 1~2 条，硬上限 2
```

**反向依赖是禁止的**：
- `SteamConnection` **不持有任何 stream 引用**，它不知道业务存在。它的死亡只影响 Session 的状态位，不影响任何 `MuxStream` 对象的生命周期。
- `MuxSession` **不做业务语义判断**（不知道 HTTP / WebSocket / 地图加载）。它只做 stream 表 + 帧路由 + 世代校验。
- `MuxStream` **不碰 Steam API**。它只跟一个本地 `net.Socket` 和一个 `MuxSession` 说话。

这三条是 0.13.3 那个架构病根的**结构性**解药：今天的 `bindLocalSocket(peer, socket)` (`steam-adapter.cjs:1824`) 里 `peer` 与 `socket` 是同一个对象上的两个字段，所以「一条 TCP 断开」与「一条 Steam 连接断开」在数据结构层面就是同一件事 —— 拆不开。分层之后它们在不同的对象上，**想连也连不上**。

### 2.3 MUX 协议 v2（定稿）

**帧格式**（规格 §十 的 `[len][type][streamId][generation][payload]` 原样采用）：

```
 偏移   0        4      5            9              13
        +--------+------+------------+--------------+-------------------
        | len:4  | type | streamId:4 | generation:4 | payload
        |  BE    |  1B  |    BE      |     BE       |
        +--------+------+------------+--------------+-------------------
        len = 9 + payload.length     （即 type+streamId+generation+payload 的字节数）
        FRAME_HEADER = 13
```

- **为什么 `len` 要存在**（保留 v1 的设计理由）：发送层会按 `maxChunk`（4 KB）把一坨字节切成多条 Steam message，没有长度前缀，帧会被切碎且无法还原。
- **`generation` 的语义**（规格 §十七）：per-stream 世代号，由**发起 OPEN 的那一侧**分配。首次 OPEN 为 1，每次因 transport 重建而重新 OPEN 时 +1。该 stream 上后续所有 `Data/Close/Reset/Window` 都必须带这个世代。
  - 接收端 `frame.generation < stream.generation` → **直接丢弃** + `stats.staleFrames++`（旧连接迟到数据，规格 §十七 硬要求）。
  - `frame.generation === stream.generation` → 正常处理。
  - 非 OPEN 帧却是 `>` → 协议违规，`Reset` 该 stream + 计数。真正的重建一定伴随 OPEN，走 OPEN 分支。
- **`streamId = 0` 保留给 session 级控制帧**（`Ping`/`Pong`），与 v1 的"0 表示没有流"一致。

**魔数**：`SHLMUX` + 1 字节版本。**版本从 `\x01` 升到 `\x02`**（帧头变了，v1 与 v2 不兼容）。
- `HELLO_BYTES = Buffer.from('SHLMUX\x02', 'binary')`，7 字节，**裸发、不带帧头，必须是干道上的第一条消息**。
- `isHello(buf)` 只比前 6 字节 ASCII 魔数；新增 `helloVersion(buf)` 读第 7 字节。**版本不认识就按 legacy 处理**（安全退回，并 emit 一次诊断），不是报错。
- `\x01` 从未发布过（0.13.3 是单连接架构），所以**不需要兼容 v1**；升版本纯粹是为了"万一有内部测试版在外"能被识别成 legacy 而不是乱解析。

**帧类型**：

| 值 | 名称 | 载荷 | 说明 |
|---|---|---|---|
| `0x01` | `Data` | 原始字节 | 一帧最多 `MAX_DATA_PAYLOAD = 64 KiB`，大于 `MAX_CHUNK` 的分多条 Steam message |
| `0x02` | `Open` | 空 | 声明 `streamId` 归我，世代 = `generation`。**reattach 也走这条** |
| `0x03` | `Close` | 空 | 本端不再发数据。**收到后不许立刻 destroy 对端 socket**（规格 §十二） |
| `0x04` | `Reset` | 1 字节原因码 | 异常释放，对端 `socket.destroy()` |
| `0x05` | `Window` | `credit:4 BE` | **端到端**背压：本端还能为这条 stream 接多少字节（绝对值，非增量） |
| `0x06` | `Ping` | 空 | `streamId = 0` |
| `0x07` | `Pong` | 空 | `streamId = 0` |

- 保留 `0x08`+ 给未来（`GoAway` 等）。
- **不做 `SESSION_HELLO` / `STREAM_REATTACH`**（规格 §十六 的"或等价物"）：重连后对每条存活 stream 重发一条 `Open(id, generation+1)` 就是 reattach。理由：少一个帧类型 = 少一整条测试路径，而 `Open` 的语义本来就是"这个 id 现在归我，从这个世代开始"。

**为什么 `Window` 是真需要的、不是摆设**：B 那侧的游戏服务端读得慢 → B 的本地 socket `write()` 返回 false → B 为这条 stream 攒的出站队列涨过 high water → B 必须能**叫 A 别再发了**。B 暂停自己的写不会让 A 停下来，只有 `Window(credit=0)` 才能让 A `pause()` 它那侧的本机 socket。初始额度 = `PER_STREAM_HIGH_WATER = 1 MiB`。

### 2.4 Stream ID 分配（规格 §十一）

规格的 Host/Client 与项目的 房主/加入者 命名**必须先钉死**，否则两边撞号：

| 项目术语 | 规格术语 | 奇偶 | 谁发起 OPEN |
|---|---|---|---|
| **加入者**（joiner，跑游戏客户端那台） | Client | **偶数 2, 4, 6, 8 …** | ✅ 本机 TCP 一进来立刻发 OPEN |
| **房主**（host，跑游戏服务端那台） | Host | **奇数 1, 3, 5, 7 …** | ❌ 当前不发起；预留给"游戏服务端反向连出去"的场景 |
| （保留） | — | `0` | session 级控制帧（Ping/Pong） |

- 常量：`STREAM_ID_SESSION = 0`、`STREAM_ID_HOST_START = 1`、`STREAM_ID_CLIENT_START = 2`。
- 加入者 `nextStreamId = 2`，每次 `+= 2`；回绕后从 2 重来并**跳过还在 `streams` 里的 id**。
- 房主侧**只接受** OPEN 分配的 id，自己不发 OPEN；`openStream(peer, streamId)` 的 id 一律来自帧。⇒ 0.13.3 里"加入者从 1 开始分配"要改成从 2 开始（`steam-adapter.cjs:1224` 的 `let nextStreamId = 1`）。

### 2.5 三套状态机

**(a) `SteamConnectionState`**（规格 §六 原样，一条连接一个）

```
                        ┌──────────────── relay 不可用（且从未就绪）────────────┐
                        ▼                                                      │
DISCONNECTED ──start()──► STARTING ──relay 检查──► RELAY_WAIT ──relay Current──┴──► CONNECTING
     ▲                                                                                │
     │                                                            Steam 回调 Connected│
     │                                                                                ▼
     │                                                              ┌─────────── CONNECTED
     │                                                              │                │
     │                        Steam 回调 ProblemDetectedLocally      │                │ Steam 回调
     │                        / ClosedByPeer（★ 只认这一条连接的）    │                │ ClosedByPeer
     │                                                              ▼                ▼
     └──────────────── CLOSED（终态，仅 close() 主动调用）         DEGRADED ◄─────────┘
                                                                     │
                                                        BACKOFF（退避计时中，不发新连接）
                                                                     │
                                                          退避到期 ──► CONNECTING
```

**关键**：进 `DEGRADED` / 重试的**唯一**触发源是**这一条 SteamConnection 自己的** `onConnectionStateChange` 回调。**Steam 登录 / CM / backend 的任何状态变化都不接进这个状态机**（规格 §八）。⇒ 规格 §三十四-③「Steam CM disconnect → close all P2P」在本方案里**结构上不可能发生**，不是靠 if 挡住的。

**(b) `SessionState`**（规格 §十五/§十六，一个远端玩家一个）

```
IDLE ──► OPENING ──► ACTIVE ─┬─► DEGRADED ──► ACTIVE      （Primary 掉：streams 一个都不销毁）
                             ├─► RECOVERING ──► ACTIVE    （新 Primary 建成 → 逐条重发 Open，flush queue）
                             └─► CLOSED                   （业务侧主动停，或超过 grace 期仍无 transport）
```

- 进 `DEGRADED` 时对每条存活 stream：**不 destroy、不 end**，只把后续数据写进各自的 `queue`（受水位约束）。本机 socket 到水位才 `pause()`。
- grace 期 `SESSION_RECOVER_GRACE_MS = 60000`（规格 §七 的退避序列 1+2+4+8+15+30 = 60 s，正好压在窗口内）。超时仍无可用 transport → `CLOSED`，所有本机 socket **`end()` 而不是 `destroy()`**，让浏览器拿到明确断开而不是连接重置。
- `RECOVERING` 的具体动作：对每条 `state !== CLOSED` 的 stream 记 `generation += 1`，发 `Open(id, generation)`，收到对端 OPEN 确认后把 `queue` flush 出去。

**(c) `MuxStreamState`**（规格 §十二）

```
OPENING ──OPEN 发出──► OPEN ──本地 end / 收到 Close──► HALF_CLOSED_LOCAL
   │                     │                                       │
   │                     │ 收到 Close                            │ 两个方向都 Close 完
   │                     ▼                                       ▼
   │              HALF_CLOSED_REMOTE ──────────────────────► CLOSED（socket.end()）
   └── 出错 / 协议违规 / 被 Reset ──► RESET ──► CLOSED（socket.destroy()）
```

- `CLOSED` 用 `end()`，`RESET` 用 `destroy()`。**两处严格区分。**
- **数据优先于最终 Close 是结构性的**：`Close` 帧与 `Data` 帧走**同一条有序队列**（Steam 可靠通道 + 同队列），所以"最后一段字节还没写出去就 destroy"这个 0.13.3 的坑（`3f62d07` 修的那个）在多路复用下**不可能复现**。

### 2.6 Retry 与 Relay 闸门（规格 §七 / §八）

**退避**：`RETRY_BACKOFF_MS = [1000, 2000, 4000, 8000, 15000, 30000, 60000]`，第 n 次取 `RETRY_BACKOFF_MS[Math.min(n, 6)]`，实际等待 `= base * (0.8 + Math.random() * 0.4)`（±20% jitter）。

**闸门 `canOpen()`**：

1. **relay 不可用（且从未就绪）⇒ 拒绝新建连接**，状态停在 `RELAY_WAIT`，**不排新的重试计时器**。⇒ 规格 §三十四-④「无限 retry」与 §三十二 Test7「不能 retry storm」由这条保证。
2. relay 从不可用 → `Current` 的**事件里只创建 1 条**；它在 `CONNECTED` 稳定 `BACKUP_ARM_DELAY_MS = 30000` **之后**、且 `session.activeStreams >= 8`，才考虑补 Backup（规格 §六 的"业务量足够"）。
3. **`MAX_TRANSPORT_CONNECTIONS = 2`（Primary + Backup），任何时刻不超过 2。** 规格 §三十四-②「固定创建 3/4/8 条」由这条保证。

**relay 状态单点采集**（`network/relay-status.cjs`）：`initRelayNetworkAccess()` 在 `initSteamSdk` 之后**立刻**调用（不再等第一次 TCP，规格 §五），随后**由 MuxScheduler 的统一 deadlines**每 5 s `getRelayNetworkStatus()` 一次，**只在 `availability` 变化时 emit**。快照字段取 `RelayNetworkStatus`：`{availability, availabilityName, pingMeasurementInProgress, anyRelayAvailability, debugMessage, at}`。可用性判定用 `ESteamNetworkingAvailability.Current === 100`；`Failed/CannotTry/Previously/Retrying`（≤ -10）一律算不可用。

### 2.7 Backpressure（规格 §十三）

`BackpressureController` 是**唯一**的 pause/resume 决策点。两级水位：

| 级别 | High | Low | ≥ High 的动作 | ≤ Low 的动作 |
|---|---|---|---|---|
| 每条 stream（出站 queue） | **1 MiB** | **128 KiB** | 本机 `socket.pause()` + 发 `Window(credit = 剩余额度)` | `socket.resume()` + `Window(credit 恢复)` |
| 整个 Session（所有 stream 的 `queuedBytes` 之和） | **8 MiB** | **2 MiB** | 暂停**所有**本机 socket | 全部 `resume()` |

**常量直接复用现成的**（E.3 已记）：`PEER_OUT_HIGH_WATER = 1 MiB`(`steam-adapter.cjs:275`)、`PEER_OUT_LOW_WATER = 128 KiB`(`:277`)、`PEER_OUT_MAX_WATER = 8 MiB`(`:279`) —— 三个值正好分别对应「每流 high / 每流 low / 全局 high」。新增 `GLOBAL_LOW_WATER = 2 * 1024 * 1024`。

`PEER_PAUSE_ABORT_MS = 30000`(`:281`) 的强断语义**收窄**：只在 Session 已经 `DEGRADED` 且无可用 transport 时才允许走到 `end()`；**`ACTIVE` 状态下永不因为积压断流**。⇒ 规格 §三十四-⑦「无限 buffer」由水位 + 硬上限保证；`queuedBytes` / `maxQueuedBytes` 进 `NetworkHealth`（规格 §十三 的"必须可观测"）。

### 2.8 单一调度器（规格 §十八）

`MuxScheduler` 是网络层**唯一**的 ticking 实体，自续 `setTimeout(step, 4)`（实测 11~17 ms/tick，见 `steam-adapter.cjs:165-166` / `:528`）。每 tick 依次：

1. `steam.runCallbacks()` —— 收下 `startCallbackLoop`(`:178`) 的现有逻辑；
2. **收包**：房主 `receiveMessagesOnPollGroup(pollGroup, …)`(`:1048`) / 加入者对每条 SteamConnection `receiveMessages(conn, …)` → 交给 MuxSession 解析派发；
3. **发送**：按公平队列（round-robin + 按 stream 加权）把各 stream 的 queue 搬成 MUX 帧 → `sendChunk` 4 KB 分片 → `sendMessage`。**控制帧优先级**（规格 §二十七）：`Reset > Close > Open > Window > Ping/Pong > Data`；
4. **deadlines 到期检查**（统一的有序 deadline 表）：连接退避、stream idle 超时、ping 周期、HELLO 看门狗、健康采样、relay 状态轮询。

**要删掉的 per-peer 定时器**（E.4 表的 4 项全部收进 `deadlines`）：`peer.reconnectTimer`(`:1325`)、`peer.helloWatchdog`(`:1495`)、`peer.poolWatchdog`(`:1541` 与活代码 `:1654`)、`poolState.timer`(`:1766`)。`flushPeerOutSoon`(`:1013` 一带的"本回合末尾再发") 语义并入步骤 3。

**ping/idle**：`MUX_PING_INTERVAL_MS = 5000`（`streamId = 0` 的 Ping）；`MUX_PING_TIMEOUT_MS = 15000` 没收到 Pong → 该连接进 `DEGRADED`。stream 空闲超时 `STREAM_IDLE_TIMEOUT_MS = 300000`（5 分钟无任何方向活动才回收；HTTP keep-alive 通常短于此，WebSocket 由 Ping 保活撑着）。

### 2.9 超时分层（规格 §二十一）

| 层 | 值 | 谁管 | 能阻塞浏览器吗 |
|---|---|---|---|
| Steam transport `TimeoutInitial` | `30000`（`steam-netconfig.cjs:169`，**保留不动**） | Steam SDK | ❌ **绝不** |
| 新 stream 的业务等待 | `STREAM_OPEN_WAIT_MS = 3000` | MuxSession | ✅ 但只等 3 s，超时**回明确错误**（socket `end()`），不是干等 |
| DEGRADED 期间已有 stream 的排队 | 受 Session grace 60 s 约束 | Session | ❌ 不阻塞读，数据进 queue，到水位才 pause |
| MUX HELLO 握手 | **不再等待**（4.3：加入者首包即发 HELLO，房主被动应答，无 0 RTT 等待） | ConnectionManager | ❌ |
| 会话层就绪 | `session.cjs:33 READY_TIMEOUT_MS = 8000`（保留） | session | ❌ |

**核心改动**：加入者 `net.createServer` 回调里**不再 await 握手**。本机 socket 立刻建立、立刻分到 streamId（偶数）、数据立刻进该 stream 的 `queue`；Primary `CONNECTED` 就马上发，`CONNECTING` 就排队。⇒ 规格 §三十四-⑧「把 transport timeout 直接传给浏览器 HTTP」与 §二十一「不允许浏览器页面同步卡 30 秒」由这条保证。今天 `steam-adapter.cjs:1837`/`:1842` 那个"队列满 256 块就 `socket.destroy()`"的行为**删除**（改成水位 + `pause()`）。

### 2.10 兼容与升级路径（规格 §三十九-⑩⑪）

> **★ 本节已被 4.3 取代。** 下面这张表最初写的是"房主先开口、加入者先听不说"，
> 那个方向会直接打断旧版加入者（旧加入者会把房主的魔数当游戏数据写进浏览器，HTTP 响应被污染）。
> **最终决定是「加入者先开口、房主被动应答」**，请以 **4.3** 为准；本节只保留作决策留痕。

| 组合 | 原设计（已作废） | 现设计（以 4.3 为准） |
|---|---|---|
| **0.14.0 房主 ↔ 0.14.0 加入者** | 本方案的多路复用（v2 帧格式） | 同左，且**零延迟**（加入者首包即魔数） |
| **0.14.0 房主 ↔ 0.13.3 加入者** | 房主收非魔数首包 → `framed = false` → `attachLegacySocket()` → 与 0.13.3 逐字节一致（**但房主已先发了魔数，旧加入者会中毒**）❌ | 同上，且**房主一个字节都没多发** ✅ |
| **0.13.3 房主 ↔ 0.14.0 加入者** | 加入者先听不说，`PEER_HELLO_TIMEOUT_MS` 内听不到魔数 → `markLegacyHost()` → 整局退回透传 | 加入者的魔数会被老房主转发进游戏端口、污染请求头 ❌ —— 靠**升级顺序（房主先升）**规避，这是唯一被牺牲的组合 |
| 双方都是 0.13.3 | 与今天完全一样 | 同左 |

**为什么必须在两个方向里选一个**：在一条裸字节管道上做带内握手，先开口的那一侧，
其魔数必然会被老版本对端当成业务字节转发出去。两个方向不可能同时兼容。
选"加入者先开口"是因为用户实际的分发顺序是**房主先升级、朋友后升级** ——
这样"旧版对端"永远是加入者，"新房主 + 旧加入者"这一格必须干净。
**升级指引因此写死为：房主先升、朋友后升。**
彻底解法（带外的 virtual port 协商）见 4.3 末尾。

**升级顺序建议：房主先升。** 因为"房主先开口"，先升房主对两种组合都安全；反过来（加入者先升）会有一次"听 1.5 s 才退回老模式"的额外延迟，功能不受影响。

**回退开关**：环境变量 `SHL_STEAM_MUX=0` / 工厂选项 `mux: false` ⇒ 两侧都退回 0.13.3 单连接行为。

**关于 `poolTarget: 0`**：0.14.0 **没有池**，所以 `poolTarget` / `PEER_POOL_TARGET` / `PEER_POOL_MAX_IDLE_MS` 全部删除。但 `createSteamJoiner` 的选项签名**保留 `poolTarget` 作为 deprecated no-op**（接受并忽略）—— 因为 `test/steam-adapter.test.cjs:23` 的 `joinJoiner = (options) => createSteamJoiner({ poolTarget: 0, ...options })` 是那 59 个断言的前提，改签名会一次性打碎整份测试文件。规格 §二十三 要求的是"旧架构参数不能还在网络层起作用"，不是"测试辅助函数的选项名必须消失"——**保留 no-op 并显式标注 deprecated**，既满足规格也保住回归网。

### 4.3 ★ 兼容性更正：必须"加入者先开口，房主应答"（Phase 2 决策 13 已作废）

**发现的真问题。** 原实现里 `network/steam-adapter.cjs:932`（`attachPeer` 末尾）是**无条件**
`pushFrames(peer, [mux.encodeHello()])`，即"房主先开口"；加入者侧则"先听不说"
（等房主的魔数，`PEER_HELLO_TIMEOUT_MS = 1500` 超时后 `markLegacyHost`）。

**"房主先开口"会直接打断旧版加入者。** 0.13.3 的加入者不认识 `SHLMUX\x01`，
它会把那 7 个字节当成房主回的游戏数据、原样写进浏览器的 TCP 流 ——
HTTP 响应变成 `SHLMUX\x01HTTP/1.1 200 OK`，浏览器直接解析失败。
按分发顺序「房主先升级、朋友后升级」，这个组合**必然会发生**，不能接受。

**为什么必须二选一。** 在一条裸字节管道上做带内握手，两个方向不可能同时兼容：
先开口的那一侧，其魔数必然会被老版本对端当成业务字节转发出去。必须选一个方向兼容。

**决定：加入者先开口，房主被动应答。** 兼容矩阵：

| 组合 | 结果 |
|---|---|
| **新房主 + 旧加入者** | 加入者先发的是浏览器真实字节 → 房主看到不是魔数 → `attachLegacySocket()` 老路径，**房主从头到尾一个字节都没多发** → ✅ 完全兼容 |
| **新房主 + 新加入者** | 加入者首包就是魔数 → 房主认出 → 回 HELLO → 多路复用，**零延迟** ✅ |
| **旧房主 + 新加入者** | 加入者的魔数被旧房主转发给游戏端口、污染请求头 → ❌ 但这个组合只在「加入者比房主先升级」时出现，而升级指引是**房主先升**，所以不会发生 |

**因此：**

- 加入者建立干道后，**把 HELLO 作为这条 Steam 连接上的第一条消息立刻发出去**（任何本机业务字节之前）。
- 房主的 `attachPeer()` **不再**发 HELLO；改成在 `pump()` 的 `if (mux.isOurHello(data0))` 分支里、
  认出对端是新版之后才回 HELLO。
- `helloWatchdog` / `markLegacyHost` **不再用作"判定房主是不是新版"的手段**：
  新房主是被动应答的，永远等不到主动魔数，留着它只会让"新+新"在 1.5 秒后错误地退回老路径、
  **把多路复用整个废掉**。若仍需要看门狗，只能当诊断用（记录"房主一直没应答"），
  **绝对不能在超时后把 `framed` 置成 false 或调用 `markLegacyHost()`**。
- 房主侧一个副带效果：房主在收到加入者的 HELLO 之前**不会往对端发任何字节**，
  所以"连上但还没收到任何消息"的那一瞬间 `game.connections()` 是 0（房主还没开游戏端口连接）。
  `test/steam-adapter.test.cjs:110` 那条既有失败用例断言的正是老行为（连上就立刻开本地连接），
  **要按新架构重写，而不是把它"修回绿色"**。

**升级指引（写进发布说明）**：**房主先升、朋友后升**。房主没升之前不要让加入者先升。

**留给后续的彻底解法（不在 0.14.0 范围）**：上面的取舍之所以必须做，是因为握手是**带内**的。
Steam Networking 本身提供了**带外**的区分手段：`connectP2P(identity, nVirtualPort, options)` 与
`createListenSocketP2P(nVirtualPort, options)` 的 **virtual port**。
若加入者并行尝试 virtual port `1`（多路复用）与 `0`（老版），房主同时监听两个端口，
则"旧房主 + 新加入者"会因为 port 1 没有对应 listen socket 而**直接连不上**（不是超时、不是污染），
加入者静默走 port 0 —— 两个方向都零污染、零延迟，连升级顺序都不需要。
没有现在就做，是因为这要求房主开两个 listen socket、加入者并发两条连接、
`SteamConnectionManager.MAX_TRANSPORT_CONNECTIONS = 2` 的语义也要跟着调整，
而且**必须先确认真实 `steamworks.js` binding 对非 0 virtual port 的支持情况**
（规格 §五：禁止凭空假设 API 存在）。留作 0.15.0 或 0.14.x 的加固项。

## Phase 5 — 删除旧 Pool（已完成）

规格 §四 的要求是**让这套架构本身消失**，不是"把 `POOL_TARGET=4` 改成 3"；§二十三 与

所以这一 Phase 做的是**整段移除**，并且把删除依据留在代码里（见下），免得几个月后有人

### 5.1 删掉的依据（0.13.3 现场账本，写在墓碑注释里）

在一次 12 分钟的真实会话（292 行日志）里：

- 本机连接进来 **53 次命中池子 / 62 次临时握手** —— 命中率只有 **46%**。
- 池子里每条连接**握手要 30 秒**，而它的寿命只有 **27~40 秒**
  （`PEER_POOL_MAX_IDLE_MS = 45000` × 随机 0.6~0.9）—— 造出来就是为了等它死。
- 纯握手连接的耗时分布：30s×11、29s、27s、24s、22s、16s、11s、31s、35s、36s。
- 池子自身 churn：累计开 83 / 就绪 67 / 命中 52 / 未命中 57 / 换新 12 / **自死 15** / 均寿 31s。
- 最要命的一条：六条连接同时扑上来时池子是空的，日志原样是
  `本机连接进来 127.0.0.1:56289 —— 临时握手（池子当时是空的）`（56289/49616/63811/52515/53044/55828 六连发），
  前面紧跟三条 `Steam原因=5003（★传输层超时） 存活=30s 上行=1KiB 下行=0KiB`。

根因是**结构性的**：`refillPool()` 串行递归、一次只开一条，而每条要 30 秒；寿命又只有 27~40 秒。
**增速永远追不上消耗**，池子在任何真实负载下都会退化成"临时握手"。这与"改小目标条数"无关 ——
只要模型是"一个本机 TCP 需要一条独占的 Steam 连接"，这个问题就无解。

## Phase 6 — reconnect / migration（已完成）

规格 §十六 的原话是"**不要把 Steam reconnect 和 Minecraft reconnect 混在一起**"，
§十五 是"`SteamConnection` 断开时 Session 不应立即销毁，可进 `DEGRADED/RECONNECTING`，
新连接建立后重新绑定"。落到这一版代码上就是一句话：

> **干道（transport）断了，跑在它上面的本机连接（stream）一条都不许断。**

0.13.3 的做法正好相反：一条本机 TCP = 一条 Steam 连接，Steam 连接一断就把浏览器那条
TCP 一起 `destroy()`。用户看到的就是白屏、地图重新下。0.14.0 把这两层的生命周期拆开。

### 6.1 三层结构（规格 §十五）

```
Session（= 加入者这一侧的整个隧道会话，活到用户 stop）
  └─ Trunk / SteamConnection（干道：Primary；干道断了就换一条新的）
       └─ Stream 1..N（本机 TCP 连接：浏览器、游戏客户端 —— 它们的生命周期与干道无关）
```

`stats` 里对应三组计数必须分开看，混起来就会得出错误结论：

| 计数 | 含义 | 增长时机 |
|---|---|---|
| `trunkCreated` / `trunksReady` | **干道**累计开过 / 就绪几条 | `spawnTrunk` / 收到 Connected |
| `totalStreams` | **累计开过几条流**（= 这一局开了多少条本机连接） | 只在真的新建流时 +1，**认回不算** |
| `streams` | 此刻在跑几条流 | 开/关流时重算 |
| `streamsParked` / `streamsMigrated` / `streamsMigrateExpired` | 寄存了 / 原地复活了 / 宽限期内没救回来的流 | 干道断、重挂、清扫 |

### 6.2 两侧各做了什么

**加入者侧（`createSteamJoiner`）**

- `orphanStreams: Map<streamId, stream>` —— 干道断掉之后，挂在它上面、**本机 socket 还活着**
  的流寄存到这里，键就是流号（加入者的流号全局唯一且是偶数，见规格 §十一）。
- `parkTrunkStreams(peer, reason)` —— 把 `peer.streams` 摘下来、`stream.trunk = null`、
  记 `parkedAt`，**不动本机 socket 一个字节**。emit 一条 `notice` 告诉用户"寄存了 N 条，等 8 秒"。
- `bindStream` 的 socket 回调一律读 `stream.trunk`（**不再读闭包里的 `trunk`**）——
  换挂要成立，归属就必须是活的。寄存期间（`!owner || owner.dropped`）浏览器发来的字节
  **攒进 `stream.parkQueue`**（上限 `STREAM_PARK_MAX_BYTES = 512 KiB`，超了才断），
  **不丢也不计 `stats.dropped`**：那是请求正文，丢一个字节就是请求损坏。
- `resumeOrphanStreams(peer)` —— 新干道谈妥（听到房主魔数应答）之后调用：
  `stream.generation += 1`（规格 §十七）、发 `OPEN(streamId, 新世代)`，
  **然后**才把 `parkQueue` 里的字节按原顺序补发（带新世代）。
- `sweepOrphanStreams(now)` —— 超过 `STREAM_MIGRATE_GRACE_MS = 8000` 还没等到新干道的流
  才真 `destroy()` + `stats.streamsMigrateExpired += 1` + emit `stream-left`
  （`kind: 'TunnelClosed'`，理由是"干道断了以后 8000ms 内没能重新挂上"）。
- `dropPeer(peer, { parkStreams })`：干道死 → 寄存；**协议错乱（`feedDecoder` 解帧抛错）→
  `parkStreams: false`**，走 `closeTrunkStreams` 真收掉。理由写在代码里：已经串了位的
  字节原样搬到新干道上只会让错位继续传播，必须让客户端从干净状态重来。
- `stop()` 里 `parkStreams: false` + 清空 `orphanStreams` —— 会话都停了，没有"下一条干道"会来接。

**房主侧（`createSteamHost`）**

同样的三件事，方向相反（对象是"游戏端口那条本机连接"）：

- `stream.owner = peer`，所有 socket 回调读 `stream.owner` 而不是闭包里的 `peer`。
- `parkPeerStreams` / `adoptOrphan` / `sweepOrphans`，外加 `destroyPeerStreams`（真收摊）。
- `openStream(peer, streamId, generation)` 先查 `orphanStreams`：**同一个流号 + 世代不倒退**
  ⇒ 认回（`stats.streamsMigrated += 1`，`stream.migrations += 1`），补发寄存期间游戏服务
  吐出来的字节；世代更旧的当成迟到帧，不复用那个 socket（免得两代流写同一个 socket）。
- `handleStreamFrame` 里 `stale` 直接丢、`future` 只 `RESET` 那一条流（规格 §十七 / §二十五）。

### 6.3 关键设计取舍

1. **为什么是 8 秒，而不是"一直等"**：干道断多半是中继换路 / CM 抖一下，重挂代价几十毫秒
   到一两秒，远小于让浏览器重拉整页；但必须有上限，否则一条死流会永远占着游戏端口那条连接，
   而客户端早已不会再来。8 秒 ≈ 一次完整重连 + 四次退避窗口（规格 §七 的 `1s/2s/4s`）的余量。
2. **为什么 OPEN 必须排在补发字节之前**：房主看到 `OPEN` 才会把游戏端口那条连接认回来；
   顺序反了，那段字节会撞上一个"房主那边还不存在的流号"，被计入 `stats.dropped` 丢掉。
3. **为什么世代 +1 而不是沿用**：旧干道上迟到的 `DATA(stream=8, generation=3)` 必须被丢掉
   （规格 §十七）。沿用旧世代就分不清"复活后的新字节"和"旧连接的迟到字节"，
   结果是旧字节被写进复活的流里 —— 表现为响应内容错乱，比掉线更难查。
4. **为什么不自己造计时器**：清扫挂在本来就 4ms 一轮的泵上，用
   `sampleState.lastOrphanSweepAt` 把周期压到 `ORPHAN_SWEEP_MS = 500`。
   规格 §十八 要求整个网络层只有一个调度器；`ts()` 里也写过，多计时器本身就是现场问题之一。

### 8.2 端到端那一层是怎么搭起来的

前面的测试各自钉住一侧。规格真正要问的是**跨两侧**的问题 —— 「25 条本机 TCP 过去，Steam 层是不是
还只有 1 条」这件事，只看任何一侧都答不了：加入者那边只能数"我建了几条"，房主那边只能数"我收了几条流"。
所以 `test/phase8-acceptance.test.cjs` 把**两侧真正的适配器**同时跑起来：

```
游戏服务（echo / sink） ← 房主适配器 ← 房主假 SDK
                                          ↑↓ 桥（1ms 一轮）
                       加入者适配器 ← 加入者假 SDK
                            ↑
                      本机 TCP 客户端
```

桥的两个方向：加入者 `state.sent` → 房主 poll group；房主 `state.sent` → 加入者 `receiveMessages`。三个设计要点：

- **桥是动态的**。加入者每新开一条干道（迁移时会这样），桥就在房主那一侧补一次
  `Connecting` + `Connected`，让房主真的经历"又有一个对端连进来了"。静态桥（只认第一个连接号）
  会让迁移用例卡在"新干道的魔数根本没送到房主"上 —— 那是脚手架的错，不是产品的错。
- **桥抽干 `state.sent`**（而不是只读不删）。Test12 要传 32MB，留着不放会让假 SDK 自己变成内存泄漏，
  那就测不出真实的内存行为。
- **tap 按连接号索引**，各自留 128KB。迁移之后线路上会有两个魔数，旧的"只切开头 7 字节"会当场抛
  `EMUXFRAME`（把第二个 `SHLMUX\x01` 当成帧头解，长度读成 1397247053）。

### 8.3 写这套测试时踩的坑（都是测试代码自己的错，产品代码一行没改）

| 现象 | 真因 | 修法 |
|---|---|---|
| Test4 花了 **800 秒**、断言却全过 | 标签 `` `Q${padStart(3)}` `` 是 4 字节，而我 `collect(socket, 5, …)` 要 5 字节 ⇒ 每次都等满 8 秒超时才 resolve | 标签定长到与 `collect` 一致（`Q0000` = 5 字节），Test4 回到 **3.1 秒** |
| Test2/Test3 `3 !== 4` | 同上，`` `P${padStart(2)}` `` 是 3 字节 | 定长 4 字节 |
| Test9 死锁 8 秒超时 | 静态桥丢掉了新干道的消息 | 桥改成动态 `admit(handle)` |
| Test11 把**自己上行的回声**当成下行 | 用的是 echo 服务器 | 新增 `startSinkServer()`（只收不回），并且现在能同时断言上行顺序 |
| 全文件 7 条一起 30ms 红、进程还挂住 | tap 少了 `downBytes` Map，桥里 `undefined.get()` 抛在 `setInterval` 里；同时 `lb` 声明在 `try` 外，`startLoopback` 一抛就把游戏服务器漏在外面 ⇒ 表现成"整个文件卡死" | 补 `downBytes`；`let lb = null` + `finally` 里 `if (lb) … else await game.close()` |
| Test9「新干道上应当重发 OPEN」 | `streamsMigrated` 在**入队**那一刻就涨了，而字节要等下一个泵周期才上线 | 改成 `waitFor(() => upFrames(trunkB).some(isOpen))` —— 等线路，不等计数 |

**教训**：`h.collect(socket, n, timeout)` 在超时的时候**会照常 resolve**（返回已有字节），
所以"期望字节数写大了"不会红，只会**变慢**。写这类用例时字节数必须定长且与 `collect` 严格一致，
否则一次笔误就是十几分钟的测试时长，而且看起来还全绿。
