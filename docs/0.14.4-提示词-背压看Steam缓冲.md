# 提示词：修掉「Steam 发送缓冲排队 6.5 秒」—— 让背压看对信号

## 你的任务

在 **Stronghold Link** 里修一个已经定位好的延迟缺陷：房主 → 加入者的游戏数据不是卡在链路上，而是排在 **Steam 自己的可靠发送缓冲**里（实测最坏 **6486 ms**、p95 **5765 ms**、中位 **1688 ms**）。根因是**我们的背压水位只看"我们自己"的出站队列**，而那个队列在任何时刻都是 0 —— 数据一读进来就立刻塞给 Steam，于是本机游戏 socket 从来不暂停，Steam 那 2 MB 发送缓冲被灌满。

**这个任务不是调参，是改背压信号源。**

## 根因（两条，都有代码依据）

**① 天花板 256 KB/s 是"有意保留的出厂值"。**
`network\steam-netconfig.cjs:136-152` 的 DEFAULTS 里 `sendRateMin: null, sendRateMax: null` ⇒ 我们不下发这两个值，Steam 用出厂值 `SendRateMin = SendRateMax = 262144`；而 Valve 的 `SNP_ClampSendRate()` 在 `nMin == nMax` 时会**关掉带宽估计**、把速率钉死。附带事实：下发 `0` 会被夹成 1024 B/s；ENV `SHL_STEAM_SEND_RATE` 同时映射这两个字段（`:192-193`），在 APPLY_ORDER 里（`:211-212`）；`sendBufferSize: 2 * MB`（`:130`），缓冲满时 `sendMessage` 返回 `k_EResultLimitExceeded`。**这个天花板本身不要动**——项目注释里有历史教训：把它钉成 4 MB/s 在 120 ms RTT 的公网中继上有害（12.6 KiB 的文件卡 2606 ms，两条并发流合计 182 KiB/s 反不如单流 430 KiB/s）。

**② 背压看错了信号（真正的缺口）。**
`network\steam-adapter.cjs:517-533`：

```js
function applyBackpressure(peer) {
  if (!peer || peer.stalled) return;
  const backlog = peerOutBytes(peer);              // ← 只看我们自己的队列
  if (backlog >= PEER_OUT_MAX_WATER) { /* stalled + destroy */ }
  if (backlog >= PEER_OUT_HIGH_WATER && !peer.paused && peer.socket && !peer.socket.destroyed) {
    peer.paused = true; peer.pausedAt = Date.now();
    try { peer.socket.pause(); } catch { }
  }
}
```

水位定义：`PEER_OUT_HIGH_WATER = 1 * 1024 * 1024`（`:327`）、`PEER_OUT_LOW_WATER = 128 * 1024`（`:329`）、`PEER_OUT_MAX_WATER = 8 * 1024 * 1024`（`:331`）。全部衡量的是**我方 egress 队列**（`peerOutBytes`），而真实堆积在 **Steam 的 `pendingReliable`**；我方队列恒 0 ⇒ 水位永远碰不到 ⇒ 本地游戏 socket 从不暂停 ⇒ Steam 的 2 MB 缓冲被灌满，后面的包排队 6.5 秒。恢复路径 `resumeOrAbort(peer, written)`（`:547-561`）用 `lastProgressAt` 判"还在动"（`:555`），超 `PEER_PAUSE_ABORT_MS = 30000`（`:333`）就 destroy；`flushPeerOut`（`:563-574`）走 `egress.planOut(peer, tuning ? tuning.fairQuantum : undefined)` + `sendChunk(..., {channel:'reliable'})`。

**③ 0.14.3 的按流公平调度在这个场景用不上**：Minecraft 只有 1 条流，队头阻塞发生在游戏自身的 TCP 序列与 Steam 可靠队列里，应用层没有可重排对象。所以这个任务**不要**去动 `network\egress-queue.cjs` 的调度策略。

## 要你做的事

1. **先只读取证**：写一个不改发送路径的现场脚本，把 `pendingReliable`（Steam 连接级）与 `peerOutBytes`、本地 socket 的 `writableLength` 在时间轴上对齐打印，确认"我方队列恒 0、Steam 队列反复冲上 1.5 MB"这个结论在你的复现里成立。信号其实已经在进程里了——`network\net-latency-diag.cjs` 每 1 Hz 就在采 `pendingReliable`，**复用它，不要新增第二个采样器**（网络层的既有约定：只允许一个调度器/一个诊断源）。
2. **改背压信号源**：让 `applyBackpressure()`（以及恢复判据 `resumeOrAbort()`）在**我方队列**之外，同时看 Steam 侧的在飞/待发字节（`pendingReliable`、必要时含 `pendingUnreliable` 与 Steam 报的 `queueMs`）。设计一个**双水位**：例如 Steam 待发超过 ~256 KiB 就暂停本地 socket，降到 ~64 KiB 就恢复。目标：最坏排队从 6.5 s 压到 1~2 s，**吞吐不许塌**（暂停期间必须靠"Steam 队列在排空"来恢复，不能等 30 s 的 abort 兜底）。
3. **处理连接级 vs 流级**：`pendingReliable` 是 Steam **连接**级指标，而 `peer` 是本机 TCP 连接；0.14.0 之后一条干道（trunk）可以承载多条流。用连接级信号暂停本地 socket 会**同时**停掉这条干道上的所有流——请在设计里明确这一点，并给出你选择的策略（可选：按"每条流的在飞字节"分摊水位、只暂停贡献最大的流、或整条干道一起停）。这是本次改动最需要想清楚的地方，写进报告。
4. **别踩已有的坑**：
   - `resumeOrAbort` 的注释明确写过：判断"还送得出去"必须看 `lastProgressAt`，不能看 `lastSendAt`——否则一条"慢但在动"的连接会被当成死的，30 秒后准时 destroy（现场表现是"几 MB 的大文件每传 ~28 KB 必断、小文件全好"）。你的新水位不能让这个误杀复活。
   - 暂停本地 socket 不能停太久：Minecraft/浏览器都有自己的读超时，停到几十秒会把玩家踢掉。恢复条件必须比现在更快更灵敏。
   - 不能丢字节：可靠流上戳一个洞比丢数据更糟（见 `dropFromOut` 的注释，`network\steam-adapter.cjs:495-510`）。
5. **加回归测试**（`node --test`，参照 `test\steam-adapter.test.cjs` / `test\mux-backpressure.test.cjs` 的写法）：Steam 待发超阈值 ⇒ 本地 socket 被 pause 且 `sendRateMin/Max` 仍为 null；待发降到低水位 ⇒ resume；长时间"慢但在动" ⇒ **不得**触发 `stalled`/destroy。
6. **给回滚开关**：新增调参项走 `network\link-tuning.cjs` 的既有模式（ENV + `BOUNDS` + 默认值），例如 `SHL_STEAM_BACKLOG_HIGH` / `SHL_STEAM_BACKLOG_LOW`，默认开启；把"设成 0 / 不设置就退回 0.14.3 的行为"写清楚。默认值要有理由，并在报告里给出你实测的两三组水位对比。

## 附：原始结论（一句话版）

他卡不是链路远（RTT 只有 57–62 ms），是**排队**：Minecraft 服务端推区块的瞬时需求顶满了 Steam 给这条连接分的 **256 KB/s** 出厂天花板，多出来的可靠数据堆在 **Steam 自己的发送缓冲**（峰值 1.62 MB），最坏队头阻塞 **6.5 秒**；而我们的背压水位只看**我们自己**的队列（恒 0），所以本地游戏 socket 从来不暂停。修法就是让背压看对信号。
