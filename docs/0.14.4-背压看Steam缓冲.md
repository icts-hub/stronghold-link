# 0.14.4 性能修复：出站背压改看 Steam 待发可靠数据

## 1. 结论

`network/steam-adapter.cjs` 的背压信号从「只看我们自己的出站队列（`peerOutBytes`）」改为「再看 Steam 连接的 `pendingReliable`（待发可靠字节数）」，并按**连接级双水位滞回**暂停该连接上游的全部本机数据源 socket。

选型：**A 方案，高水位 256 KiB / 低水位 64 KiB**（与 `network/link-tuning.cjs` 的默认值一致）。选型依据是 `tools/steam-backpressure-model.cjs` 的确定性模型矩阵，不是真机结论。

## 2. 现场证据（0.14.3 实测）

## 3. 根因

| # | 置信度 | 位置 | 结论 |
|---|--------|------|------|
| ① | **已验证事实** | `network/steam-adapter.cjs` 的 `applyBackpressure` | 只读 `peerOutBytes(peer)`；Steam 发送缓冲（`network/steam-netconfig.cjs` 的 `sendBufferSize`，2 MiB）灌满之前 `sendMessage` 一律回 success。同一份现场日志里 `pendingReliable` 峰值 1.62 MB 而 `globalQueueBytes` 全程为 0，两边读数对不上即为证据 |
| ② | **已验证事实（代码路径）／强推断（真机影响）** | 同文件的暂停逻辑 | 只 `peer.socket.pause()`，而多路复用模式下 `peer.socket` 恒为 `null`（`network/steam-adapter.cjs` 的注释与 `collectSourceSockets` 的现状可证）；因此老代码在多路复用路径上没有任何东西被暂停。真机上"如果当时停了会好多少"无法回放验证 |
| ③ | **强推断** | `resumeOrAbort` 的 30 s 看门狗 | 暂停期间不再 flush，`lastProgressAt` 不再更新，正在慢慢排空的健康连接会被误判为死连接并 destroy。推理链成立，但没有 0.14.3 现场日志直接记录过这种误杀 |

未证实的假设（本次不作为依据）：真实校园网每流上行上限低于 256 KB/s；Steam 中继路径（`hkg`）本身贡献了队列时间。两者都只能用双侧升级后的真机 A/B 排除。

## 5. 候选方案与模型评分

工具：`tools/steam-backpressure-model.cjs`（确定性 tick 模型，管道为 生产端缓冲 → 我们的出站队列 → Steam 可靠缓冲 → 按速率放行 → RTT，字节严格 FIFO、不重排、不丢失）。
矩阵 runner：`node tools/steam-egress-sim.cjs --backpressure --bp-json tools/steam-backpressure-sim.json`。
场景：`heavy`（区块 1 MB/s + 50 Hz 移动包，链路 256 KB/s、RTT 60 ms）、`sustained`、`burst900`、`slow`、`multi`、`lossy`（2% 丢包 + RTT 100 ms）、`rtt20`、`rtt120`、`cap`。

|------|------|--------------|----------|--------|--------|--------|----------|------|
| `off`（0.14.3） | 不暂停 | 8000 ms | 8000 ms | 1 | 1 | 1 | 0 | — |
| **A** | 256/64 KiB | **1133 ms** | 1237.8 ms | 0.6334 | 0.2266 | 1.0004 | 9.78 | **是（选中）** |
| A128 | 128/32 KiB | 568.8 ms | 742 ms | 0.5298 | 0.1552 | 1.0002 | 19.56 | 是（翻转约 2×） |
| A512 | 512/128 KiB | 2011.4 ms | 2011.4 ms | 0.7855 | 0.4146 | 1 | 4.78 | 否（峰值超 2000 ms） |

- `slow`（180 KB/s < 链路）：六种策略逐项相同（待发 p95 0 KB、移动包 60 ms、吞吐 181.28 KB/s、翻转 0）⇒ 生产端不超链路时新背压不介入。
- `lossy`：吞吐整体 89.7–90.0 KB/s；重传被记账，账仍平。
- 择优规则（机械执行）：零丢失 → 吞吐 ≥ 基线 90% → 最坏排队 p95 ≤ 1250 ms 且峰值 ≤ 2000 ms → 翻转最少 → 延迟最低 ⇒ 选出 **A**。

## 6. 实现与调用链

| 文件 | 改动 |
|------|------|
| `network/steam-adapter.cjs` | 新增 `STEAM_STATUS_MIN_INTERVAL_MS = 20`、`readSteamRealtimeStatus()`、`steamBacklogBytes()`、`sampleSteamBacklog()`、`pumpPeerBackpressure()`、`collectSourceSockets()`、`pauseSourceSockets()`、`resumeSourceSockets()`；`applyBackpressure()` 增加 Steam 高水位分支并把暂停/销毁作用到全部数据源 socket；`resumeOrAbort()` 要求两路水位都降下来才恢复；房主泵与加入者泵每 tick 先 `pumpPeerBackpressure()`；`openStream` / `bindStream` / `bindLocalSocket` 绑上新 socket 时若已暂停则一并暂停；导出上述新函数 |
| `network/link-tuning.cjs` | 新增 `steamBackpressure`（默认 `true`）、`backlogHigh`（默认 262144）、`backlogLow`（默认 65536）及 BOUNDS/ENV；`backlogLow > backlogHigh` 时压到高水位并记 `notes` |
| `tools/steam-backpressure-model.cjs`（新增） | 确定性背压模型（`simulateBackpressure`、`SCHEMES`、`SCENARIOS`） |
| `tools/steam-egress-sim.cjs` | 新增 `--backpressure` 模式与 `--bp-json`：跑策略×场景矩阵、打印对照表、按优先级择优 |
| `test/steam-adapter.test.cjs` | 新增 14 条背压用例 |
| `test/link-tuning.test.cjs` | 新增 4 条参数用例 |
| `test/steam-backpressure-model.test.cjs`（新增） | 12 条模型回归用例 |

调用链（每 tick，房主 `createSteamHost` 的泵与加入者 `createSteamJoiner` 的泵相同）：

```
pump()
  → pumpPeerBackpressure(steam, peer, tuning)
      → sampleSteamBacklog()          // 20ms 节流，读 getConnectionRealTimeStatus().pendingReliable
      → backlog >= tuning.backlogHigh ? applyBackpressure(peer, tuning) : 不变
  → resumeOrAbort(peer, flushPeerOut(steam, peer, sendChunk, tuning), tuning)
      → 两路水位都降下来 → resumeSourceSockets(peer)
      → 30 s 无进展（lastProgressAt）→ 标记 stalled 并销毁数据源
```

连接级作用范围：`pendingReliable` 是**连接级**指标，无法归到某条流上，因此同一连接上的流会被一起暂停。多流场景已在模型里覆盖（`multi`），真机多流未验证。

顺带修复（0.14.3 起就存在的崩溃）：`network/steam-adapter.cjs` 的 `feedDecoder()` 在协议错乱分支里引用了作用域外的 `states`，会抛 `ReferenceError: states is not defined`，把 Steam 回调循环带进 `ESTEAMCALLBACK` 致命错误（现场表现：整局应用层往返读数变成 `null`）。已改为传 `null`（`peerCloseInfo(peer, null, null, ...)`，该分支本来就走 `ProblemDetectedLocally`）。

## 7. 可靠数据、错误返回与慢连接

- 暂停只作用于**读取**本机 socket，不删除、不重排任何已入队字节；恢复后继续按 FIFO 发送。
- `sendMessage` 返回 `k_EResultLimitExceeded` 时字节留在出站队列（`egress` 未确认前缀不出队），下一 tick 重试；模型里 `limitExceeded` 峰值从 `off` 的 837 次降到 0。
- 慢连接保护：`PEER_PAUSE_ABORT_MS = 30000` 仍以 `lastProgressAt` 判定；`sampleSteamBacklog()` 在 Steam 积压变小时刷新 `lastProgressAt`，避免排空中的连接被误杀。`lastProgressAt` 未换成 `lastSendAt`。
- 读不到 `pendingReliable`（绑定缺失、连接为空、调用抛错）时行为完全退回 0.14.3：只按本机队列水位。

## 10. 真机验证与尚未验证

同机环回、真实 Steam P2P + SDR 的整机实测（`node tools/steam-latency-probe.cjs --bulk-connections 4 --bulk-payload 262144 --bulk-interval 20 --duration 20000`，4 条并发流每 20 ms 灌 256 KiB，20 s）：

| 运行 | 新背压 | 应用层往返 p50 / p95 / max | 最坏一帧的 Steam 排队 / 待发 | 结论 |
|------|--------|---------------------------|------------------------------|------|
| `latency-bp04-bulk-off-20261013-001604.json` | `SHL_STEAM_BACKPRESSURE=0` | 29 / 85 / 130 ms | 0 ms / 0 B | 基线 |
| `latency-bp04-bulk-on2-20261013-001632.json` | 默认（开） | 28 / 85 / 125 ms | 0 ms / 0 B | 无回退 |

环回链路上 Steam 发送缓冲始终为空（`可靠待发=0B`、`Steam排队=0ms`），新背压没有可介入的对象，因此这组数据只能证明「开启后不劣化」，不能证明真机收益。两次运行都复现了同一个 0.14.3 起就有的启动期协议错乱（`流多路复用帧长度不合法：774778414`，一条干道被判 `BadFraming` 后重连成功），与本次改动无关。

尚未验证：

- **真实校园网 + 真实对端的 A/B 未做**：没有跑空闲延迟 / 区块突发 / 连续游戏三场景的基线-修复对照。§5 的数字全部来自模型，不能当真机数据引用。
- 模型不含真实 Steam/SDR、拥塞控制、加密、ACK 细节与本机事件循环开销。
- 多流共享同一干道时的公平性代价只在模型里验证（`multi` 场景），真机未验证。
- 对端若停留在 0.14.3，其出站方向仍会有同样的排队（本修复是双侧生效，需两边都升级）。
- `relay=hkg`、60 ms RTT 来自一次会话；IPv6/NAT/其它中继路径未在本次改动范围内。
