## 1. 项目概览

**一句话**：Stronghold Link 是一个 Windows 桌面端的通用内网穿透 / 联机工具——它把**房主机器上的一个本机端口**（TCP 或 UDP），变成**加入者机器上 `127.0.0.1:<入口端口>` 的一条可用连接**，中间不需要公网 IP、不需要端口映射。

**它是怎么做到的**：桌面应用（Electron）在两端各跑一个会话：房主把本机游戏/服务端口挂上"通道"，加入者在本机开一个入口端口；两端的会话通过四种通道之一把字节互相搬运：

| 通道 | 是否需要外部条件 | 是否需要口令 | 典型用途 |
|---|---|---|---|
| 本地中继（TCP/UDP 端口规则） | 需要一台双方都能连到的中继机 | 需要（邀请码含口令） | 有公网服务器时最稳 |
| 本地中继 + 浏览器应用 | 同上 | 需要 | 加入者连浏览器应用（如网页控制台），点开链接即可 |
| **Steam P2P 隧道** | 双方 Steam 在线 + 自备 Steamworks SDK | **不需要口令** | 跨网络、无服务器、朋友间联机 |
| 局域网直连 | 同一局域网 | 不需要 | 不转发流量，仅提示直连地址 |

**它明确不做的事**：不解析、不修改、不压缩任何上层协议（包括 Minecraft）。Minecraft 的压缩包、长度前缀、netty 帧，对 Stronghold Link 来说都只是**不透明的字节**；程序只负责"把这些字节按原顺序、不重不漏地搬到对端"。唯一的"加工"是在 Steam 通道里做了**流多路复用与分帧**（把多条本机 TCP 塞进一条 Steam P2P 连接）。

**版本脉络**：

| 版本 | 主题 |
|---|---|
| 0.13.x | 旧架构：**一条本机 TCP = 一条 Steam P2P 连接**（连接池预热，握手 11–36 秒，churn 严重） |
| **0.14.0** | 网络架构级重构：TCP → **MUX** → Steam P2P；干掉旧连接池；引入 Primary/Backup 双连接、三层状态机、单一调度器、出站公平调度 |
| 0.14.1 | 修"首个数据包丢了就整局永久吊死" |
| 0.14.2 / 0.14.3 | 出站按流公平调度 + 1Hz 延迟诊断 + Steam 发送速率模型 |
| **0.14.4** | 背压看 Steam 待发缓冲；连接级双水位；`feedDecoder` 状态机修复 |
| 0.14.5 / 0.14.6 | 修"干道重挂时出站队列里的字节被吞掉"（迁移字节空洞）＋ 可靠确认（Ack/Resume）——**已按用户要求整体回滚**，见 §13 |

## 2. 关键设计决策

**决策一：0.14.0 起，"一条本机 TCP"不再等于"一条 Steam P2P 连接"。**

原因（写在 `docs/0.14.0-网络架构重构.md` 的 Phase 1 源码审计里）：Steam P2P 连接建立需要 **11–36 秒**；旧架构下**每一个新本机连接**（浏览器刷新、Minecraft 重连、扫描）都要新建一条 P2P，于是出现"连接池预热 → 疯狂重建 → 握手风暴"。新架构改为：

```
本机 TCP/UDP ──► 会话（Session）──► Steam P2P「干道」×1 ──► 对端会话 ──► 本机 TCP
                        └── 多条流（Stream）复用同一条干道（MUX v2）
```

一条干道建立后，新的本机连接**只是在这条干道上开一条流**（`OPEN` 帧），秒开，不再有握手等待。

**决策二：不做协议转换。** 适配器只做"字节搬运 + 分帧 + 流号复用 + 背压"，这是"不破坏任何上层协议"的前提，也是排查故障时的基准假设（§12 的排查表按这个假设组织）。

**决策三：安全层与通道解耦。** 安全（口令、密钥、加密）由 `secure-stream.cjs` / `secure-datagram.cjs` / `session.cjs` 负责；Steam P2P 通道自带 Steam 的加密与身份（且它天然要求双方互为 Steam 好友/大厅成员），因此 **Steam 路径不需要口令**。

## 3. 运行环境与依赖

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10/11 x64（打包目标只有 Windows；`electron-builder` 的 win target = `nsis` + `portable`，x64） |
| 运行时 | Electron 39.8.10（内置 Chromium 与 Node 22） |
| 开发环境 | Node.js 22+（实测 24.21.0 可用）、npm |
| 构建依赖 | `electron-builder ^26.0.0`、`esbuild ^0.28.2`、`three ^0.186.1`（devDependencies） |
| 可选依赖 | `steamworks-ffi-node ^0.11.3`（optionalDependencies；Steam 隧道必需） |
| Steam SDK | **不随仓库分发**。需自备 Steamworks SDK，把 `steam_api64.dll` 放到 `steamworks_sdk/redistributable_bin/win64/`（见 `steamworks_sdk/README.md`） |
| Steam 客户端 | Steam 隧道要求双方 Steam 在线；测试期可用 AppID **480**（Spacewar），**两端必须一致** |

**两个必须知道的坑**：

1. **缺少 `steam_api64.dll` 时，FFI 加载会直接把进程带走**（不是抛异常，是进程级崩溃）。所以程序在启动会话前会先用 `network/steam-env.cjs` 的 `diagnoseSteam()` 预检，也需要 `steam:diagnose` IPC 做界面自检。
2. **同一个 Steam 账号自连不成立**：实测 `sendReliable` 返回 `result=8` 后连接断开。Steam 隧道需要**两台不同的电脑 + 两个不同的 Steam 账号**。

### 4.2 源码运行与打包命令

```powershell
cd Stronghold-Link\source
npm install                 # 安装依赖
npm start                   # 开发模式启动（Electron）
npm test                    # 全量测试（58 个测试文件）
npm run test:single -- test/xxx.test.cjs   # 单文件测试
npm run smoke               # 打包产物 smoke 自检
npm run vendor:three        # 从 node_modules 取 three.js 到 src/ui/vendor

npm run build:dir           # 只出 win-unpacked 目录 → ..\release\win-unpacked\
npm run build               # NSIS 安装包（需要访问 GitHub 下载 electron 发行版）
npm run dist:full           # 完整版 lzma 包 → ..\release\lzma\Stronghold-Link-<版本>-win-x64.tar.xz
npm run dist:lite           # 精简版 lzma 包 → ..\release-lite\lzma\...
npm run dist:both           # 两个都出
node tools\pack-lzma.cjs    # 直接把当前 win-unpacked 打成 lzma 包
```

**完整版 vs 精简版**：完整版带 `three.js r186`、两个 GLB 模型与 288 实例的三维背景；精简版不含 WebGL 相关资源。包根都会写一份 `EDITION.txt` 标明形态（`tools/build-edition.cjs`）。

**打包配置要点**（`package.json` 的 `build` 段）：

- `appId: com.strongholdlink.tunnel`、`productName: Stronghold Link`、`output: ../release`
- `asar: true`，`files` 白名单 = `electron/ network/ src/ package.json`（排除 `*.md`、`test`、`tools`、`docs`、`release`、SDK 的 `.lib/.exp/.pdb`）
- `extraFiles`：`dist-extras` → 包根
- `electronLanguages: [zh-CN, en-US]`；`win.target = [nsis, portable]`、`arch = x64`
- `artifactName: Stronghold-Link-${version}-${arch}.${ext}`；`compression: maximum`

**0.14.4 构建产物实测**：`release\win-unpacked\resources\app.asar` = **12,744,046 字节 / 917 个文件**，内部 `package.json.version` 与 `electron/main.cjs` 的 `APP_VERSION` 均为 `0.14.4`。

## 5. 快速上手

### 5.1 Steam P2P 隧道（跨网络联机，推荐给朋友之间）

**房主侧**：
1. 启动 Stronghold Link → 连接方式选 **Steam P2P 隧道**；
2. 填**要被转发的游戏端口**（例如 Minecraft 的 `25565`，或局域网世界显示的端口如 `11111`），必要时用"监听端口探测"一键识别（`listening-ports.cjs` 会列出本机监听端口并给出建议）；
3. 启动会话 → 界面显示本机 **17 位 SteamID**，把它发给朋友。

**加入者侧**：
1. 用**另一个 Steam 账号**（另一台电脑）启动程序 → 连接方式选 Steam P2P 隧道；
2. 填房主给的 **17 位 SteamID** 与本机一个**空闲入口端口**（例如 `25566`）；
3. 启动会话 → 程序会在本机监听 `127.0.0.1:25566`，并自动打开浏览器提示页；
4. 游戏里"多人游戏 → 直接连接"填 **`127.0.0.1:25566`**。

**要点**：Steam 隧道**不需要口令**；聊天/大厅只用来交换连接信息（`steam-lobby.cjs`），数据仍然走 P2P 隧道。

### 5.2 本地中继（有公网服务器时最稳）

1. 在中继机上跑 `tools/relay-daemon.cjs`（部署说明见 `docs/中继部署.md`）；
2. 房主：连接方式选"本地中继"，填中继地址、端口规则（TCP/UDP）、口令；
3. 把邀请码（含口令）发朋友；
4. 加入者：粘贴邀请码 → 程序在本机开入口端口 → 游戏连 `127.0.0.1:<入口端口>`。

### 5.3 局域网直连

同一局域网内，程序检测到直连可用会直接提示局域网地址，不消耗中继/Steam 带宽（`route-report.cjs` 判定直连 vs 中继）。

                              └────────────────────────────────┘

### 7.2 一条本机 TCP 连接的完整旅程（Steam 通道）

**房主侧**（别人连进来）：

1. Minecraft 客户端连 `127.0.0.1:<游戏端口>` → 会话 accept 到这个 socket；
2. **干道已在**（Steam P2P 已连上且已交换开场魔数 `SHLMUX`+版本）→ 不需要握手，直接 `mux.encodeOpen(streamId, generation)` 发出去；
3. 游戏服务端写回的字节 → `socket.on('data')` → `mux.encodeDataChunks(...)`（> 64 KiB 自动切分）→ 出站队列 `egress-queue` → `flushPeerOut` 交给 Steam `sendMessage`；
4. 对端发来的 `Data` 帧 → 按流号找到对应本机 socket → 写入。

**加入者侧**（自己往对端连）：

1. 游戏连 `127.0.0.1:<入口端口>` → `bindStream` 开一条新流（流号 = 偶数自增）；
2. 若干道还没定帧（还没交换魔数），`OPEN`/`DATA` 帧先**扣在** `heldFrames` 里，定帧后 `flushHeldFrames` 一次性放行（这就是 0.14.1 "首包丢了就整局永久吊死"的修复点）；
3. 之后与房主侧对称收发。

**关键点**：TCP 的"读边界"与 Minecraft 的"包边界"没有任何关系。适配器**从不**按读取边界切数据，只按"本机 socket 写出来的字节顺序"切分（切分点只影响分帧，不影响字节序列），收到后再按顺序写入对端 socket——这是一条纯粹的字节流管道。

### 7.3 会话与握手

- **一条端口规则 = 一个通道**：会话启动时按规则列表逐条建通道；批量启动失败会回滚已建通道。
- **Steam 干道握手**：加入者先发 `SHLMUX` + 版本字节，房主应答；房主侧 4 秒没等到就重试（`trunkHelloRetryMs`），30 秒仍没有就放弃并把这条干道判失败（`trunkHelloGiveupMs`）。
- **兼容**：对端不说魔数（老版本）→ `markLegacyHost`，退回"单连接透传"老路径（此时 `framed = false`，MUX 帧不会被发出）。
- **端口生命周期**：`before-quit` 释放端口；`checkPortFree` 在启动前预检并报告占用者。

### 7.4 安全层（本地中继 / 需要口令的通道）

| 层 | 机制 |
|---|---|
| 密钥协商 | X25519 临时密钥（前向保密）+ scrypt 硬化口令 → PSK |
| 身份校验 | 双向 HMAC 标签 |
| 数据加密 | AES-256-GCM |
| TCP 记录格式 | `4 字节长度 + 8 字节计数器 + 密文 + 16 字节标签` |
| UDP 记录 | 逐包加密 + 1024 包滑动窗口抗重放 |
| 邀请码 | 携带口令（因此邀请码等同于凭据，别公开贴出） |

Steam P2P 通道**不使用**上述口令层：Steam 自身提供加密与身份，且连接前提是双方已在大厅/好友关系里。

## 8. Steam P2P 隧道与 MUX v2 协议

### 8.1 三个概念

| 概念 | 含义 |
|---|---|
| **干道（trunk）** | 一条 Steam P2P 连接。建立慢（11–36 秒），但一条就够。 |
| **流（stream）** | 一条本机 TCP 连接在干道上的化身。流号：会话 0、房主奇数（从 1 起）、加入者偶数（从 2 起）。 |
| **世代（generation）** | 流的"租约号"。干道断掉重挂时，同一条流用**同一个流号 + 世代 +1** 原地复活，两端应用**看不到连接断开**。 |

### 8.2 帧格式（v2）

```
偏移  长度  字段
 0     4    len       = 9 + payload.length（大端）
 4     1    type      帧类型
 5     4    streamId  流号（大端）
 9     4    generation 世代（大端）
13     N    payload
```

- `FRAME_HEADER = 13`；`MAX_FRAME_BYTES = 1 MiB`；`MAX_DATA_PAYLOAD = 64 KiB`（更大的写入自动切成多帧，顺序保持）
- 开场魔数：`'SHLMUX'` + 1 字节版本（当前 `MUX_VERSION = 2`）
- 解码器容错：若发现字节流里出现**迟到的重复魔数**，整段跳过而不是当成 `len = 0x53484C4D`（否则会报 `EMUXFRAME`）

### 8.3 帧类型与优先级

| 类型 | 值 | 方向/用途 | 优先级 |
|---|---|---|---|
| `Data` | `0x01` | 流数据 | 5（最低） |
| `Open` | `0x02` | 开一条流 | 2 |
| `Close` | `0x03` | 正常关闭（对端 `socket.end()`） | 1 |
| `Reset` | `0x04` | 异常重置（对端 `socket.destroy()`），载荷 1 字节原因码 | **0（最先发）** |
| `Window` | `0x05` | 窗口/信用通告 | 3 |
| `Ping` / `Pong` | `0x06` / `0x07` | 心跳与测速 | 4 |
| `Ack` / `Resume` | `0x08` / `0x09` | **0.14.5/0.14.6 引入的可靠确认，已随回滚移除** | — |

`RESET_REASON`：`Protocol 1`、`StreamLimit 2`、`Backpressure 3`、`Shutdown 4`、`Decode 5`、`Stale 6`。

### 8.4 世代检查

收到帧时比对帧里的世代与本机该流的世代：

- 相等 → 正常处理；
- **更旧（stale）** → 丢弃并计数（`stats.staleFrames`），不发 Reset（避免"迟到帧打回现场"）；
- **更新（future）** → 说明本机这条流已经过期：回一个 `Reset`、删流、销毁本机 socket。

### 8.5 出站队列与公平调度（0.14.3 起）

- 每条流一条**独立 FIFO**；流与流之间**轮转公平调度**（每回合每条流最多 `fairQuantum = 4 KiB`，起点跨 flush 记忆，避免某条流饿死别人）。
- 入队 → 达到 `outFlushBytes`（16 KiB）或调度周期到 → `planOut` 生成"计划" → 交给 Steam → **只把"Steam 已接受的前缀"出队**（`commit`）。这个"确认前缀 + 前缀出队"是 0.14.3 的核心正确性设计：Steam 只接受了一部分时，剩下的字节**留在队里**，下次继续，不会重复也不会丢。
- 老行为（`fairQueue=false` / `SHL_STEAM_FAIR_QUEUE=0`）退回 0.14.2 的干道单队列。

### 8.6 背压

| 层级 | 触发 | 动作 |
|---|---|---|
| 单流 | 出站队列 > `PEER_OUT_HIGH_WATER`（1 MiB） | 暂停读本机 socket（`socket.pause()`）——**暂停 ≠ 关闭** |
| 单流恢复 | 队列 < `PEER_OUT_LOW_WATER`（128 KiB） | 恢复读 |
| 全局 | 所有流合计 > `PEER_OUT_MAX_WATER`（8 MiB） | 硬上限：这是"响亮地失败"（收掉源 socket 并记账），不是静默丢字节 |
| 停滞看门狗 | 暂停后 30 秒（`PEER_PAUSE_ABORT_MS`）一个字节都没送出去 | 判定真死，收掉这条流并写明原因 |
| Steam 侧 | 0.14.4 起同时观察 **Steam 自己的待发缓冲**（`steamBacklog`，两个水位 `backlogHigh 256 KiB` / `backlogLow 64 KiB`） | 提前暂停，避免"我们以为发出去了、其实堵在 Steam 里" |

**设计原则**：慢但仍在前进的连接**不允许**被判死；暂停只是一种"先别生产"的信号，恢复后必须能继续传。

### 8.7 迁移与寄存（reconnect / migration，0.14.0 Phase 6）

当干道断开（Steam 报 `ClosedByPeer` / `ProblemDetectedLocally`，例如 `Relay received unexpected noconnection packet` ⇒ Steam 原因 `5010`）：

1. **不拆流**：把流对象从旧 peer 摘下来，放进寄存区 `orphanStreams`（键 = 对端 SteamID + 流号，避免第三个人抢走前一个人的流）；
2. 提示 `干道断了，先把 N 条本机连接寄存 60 秒等新干道来接`（`SESSION_RECOVER_GRACE_MS`）；
3. 新干道建好后（Primary/Backup + 退避重连），对每一条寄存的流发 `OPEN(同流号, 世代+1)`，**原地复活**，并按新世代补发寄存期间攒下的字节；
4. 60 秒内没挂上 → 超时收流并写明原因（`干道断了以后 60000ms 内没能重新挂上`）。

对 Minecraft 来说，这条连接**从未断开过**（TCP 层没有 FIN/RST），所以玩家不会被踢出。**这正是 §13 那个已知缺陷的所在**：复活时如果出站队列里还有"没交给 Steam"的字节，0.14.4 会把它连旧 peer 一起丢掉，而对端已经认为这条流是连续的 → 字节流中间出现空洞。

| `本机连接进来 127.0.0.1:xxxxx —— 走多路复用干道` | 一条新的本机 TCP 被接进已有干道（开流，不握手） |
| `干道上开了一条流 流号=N 对端=<SteamID>` | 流的建立 |
| `连接已接通 … （多路复用干道，1 条 Steam 连接承载所有本机连接）` | 干道就绪且对端说 MUX |
| `干道断了，先把 N 条本机连接寄存 60 秒等新干道来接（原因：…）` | 进入迁移流程 |
| `新干道已谈妥，N 条本机连接原地复活（世代 +1…）` | 迁移完成 |
| `流结束（<kind>）流号=N … 理由=… 存活=Ns 上行=XKiB 下行=YKiB` | 流关闭（0.14.4 的 kind/reason 文案**是硬编码的**，见 §13 的注意） |
| `连接结束（对端关掉了这条 Steam 连接）理由=… Steam原因=5010 存活=…s 上行=… 下行=…` | 干道断开及原因 |
| `隧道存量 N 条：:? 存活…s 上行…KiB 下行…KiB 残留…KiB \| End-to-end connection: connected … Sent: … pkts/sec … K/sec` | 15 秒一次的干道快照（含 Steam 自身的端到端状态与速率） |
| `[MUX] streams=N opened=N closed=N reset=N queued=N maxQueued=N stale=N dropped=N session=ACTIVE` | MUX 汇总计数（`dropped` 在流已删除后收到迟到帧时会增长，属症状不是病因） |
| `[Steam] login=ONLINE relay=100(Current/Available) transport=READY` / `[P2P] role=primary state=connected peer=…` | Steam 与 P2P 通道状态 |
| `隧道错误 阶段=game-socket 代码=ECONNREFUSED` | 转发时本机目标端口拒绝连接 |

### 10.2 1Hz 延迟诊断 `net-latency-<role>-<时间戳>.jsonl`

0.14.3 起，链路活跃时每秒一条采样（`net-latency-diag.cjs`）。字段（实测）：

| 字段 | 含义 |
|---|---|
| `pendingReliable` / `queueMs` | Steam 侧待发字节与排队时间（背压的直接证据） |
| `outBytesPerSec` | 实际出站速率（上限见 `steam-netconfig` 的 `sendRateMax`，实测约 253.7 K/s） |
| `peers[0].paused` / `.stalled` / `.framed` / `.streams` / `.outBytes` | 该干道是否处于暂停、是否被判定停滞、是否已定帧、承载流数、队列字节 |
| `streams[0].stream` / `.bytesToPeer` / `.bytesFromPeer` / `.remoteCredit` | 每条流的双向字节与信用 |
| `counters.dropped` / `.failed` / `.sendStalls` / `.totalStreams` | 累计计数 |

**怎么用**：`stalled` 若从未变成 `true`，说明"背压 30 秒停滞看门狗"没有触发过；`dropped` 的**增量**若都紧跟在"某条流结束"之后，那是迟到帧，不是丢字节。

### 10.3 四层状态判定法（排查连接问题时的顺序）

排查"连不上/掉线"时，必须把这四层分开，不能只看游戏里"玩家退出了游戏"：

| 层 | 看什么 | 健康表现 |
|---|---|---|
| ① Steam 大厅 | `收到联机邀请` / 大厅在线 | Lobby 在线**不代表**数据通道可用 |
| ② Steam 数据连接（干道） | `[P2P] state=connected`、`隧道存量 1 条` | 干道在，且**没有** `干道断了` |
| ③ MUX 流 | `干道上开了一条流 流号=N` | 流存在且没有 `流结束` |
| ④ 本机 MC TCP socket | `本机连接进来 127.0.0.1:xxxxx` | socket 未 `end/close/error` |

**"哪一端先关"**：`连接结束` / `流结束` 行里的 `存活`、`上行/下行` 与 reason 能定位；两端日志按**同一时间戳窗口**对齐。注意 0.14.4 的 `流结束` 文案无法区分"游戏侧关的"和"我们自己 destroy 的"（§13）。

### 10.4 诊断目录与探针

- `source/diag/`、`source/test-out/`：历史诊断输出。

## 12. 故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 启动即闪退 | 缺 `steam_api64.dll` 或 SDK 路径不对（FFI 会直接杀进程） | 跑 `steam:diagnose`；把 dll 放到 `steamworks_sdk/redistributable_bin/win64/`；详见 `docs/启动闪退排查.md` |
| Steam 隧道连不上，日志反复 `Steam 连接暂时建不起来，已把这条本机连接排队` | 对端没在线/不是好友/AppID 不一致/P2P 打不通 | 核对双方 AppID（测试用 480）；看 `[Steam] relay=…` 与 `[P2P] state=…`；必要时把传输偏好改 `relay` 强制走中继 |
| 同一账号自连失败（`result=8`） | Steam 不允许自连 | 用两个账号、两台机器 |
| `隧道错误 阶段=game-socket 代码=ECONNREFUSED` | 本机目标端口没人监听（游戏没开/端口填错） | 用"监听端口探测"确认游戏真实端口 |
| 端口被占用 | 入口端口/转发端口已被别的程序占用 | 会话启动前的预检会报告占用者；换端口 |
| 帧长度不合法（`EMUXFRAME`） | 字节流错位（版本不匹配或字节流被破坏） | 先确认两端版本一致；结合 §13 的日志口径判断 |
| 对端是老版本 | 收不到 `SHLMUX` 魔数 → 退回单连接透传 | 两端升到同一版本 |
| **Lobby 在线、游戏里却掉线/反复加入退出** | 见 §13（0.14.4 的干道重挂字节空洞；或对端/游戏侧问题） | 先按 §10.3 四层定位，再收集**两端**日志 |
| Minecraft 报 `unknown compression method` / `incorrect header check` / `length wider than 21-bit` | 客户端在**解码入站字节流**时发现包边界错位 ⇒ 该方向的字节流出现少/多/错 | 这是**症状**：需两端日志 + 字节账本对照，判断是隧道还是游戏侧 |

## 13. 已知问题与未验证项

### 13.1 0.14.4 的已知缺陷：干道重挂时会吞掉出站队列里的字节（**本版本存在**）

**触发条件**：Steam 干道断开 → 流被"寄存"等新干道 → 同一流号以"世代 +1"原地复活**并且**断开瞬间出站队列里还有**尚未交给 Steam 的字节**。

**机理**：寄存只搬"流对象（本机 socket）"，**不管出站队列**；队列随旧 peer 一起消失，而对端认为这条流从未断过 ⇒ 对端收到的 TCP 字节流中间少一截 ⇒ Minecraft 的 netty 解码器在包边界错位，抛 `DataFormatException`（`unknown compression method` / `incorrect header check` / `length wider than 21-bit`），玩家掉线并自动重连 ⇒ 主机侧表现为"玩家反复加入/退出"，而 Steam Lobby 一直在线。

**证据**：仓库测试可用 30,000 字节的确定性用例复现（0.14.5 曾新增该用例，回滚时一并移除）；真机日志里有 19 MB 下行后干道断开并寄存流的现场。

**修复状态**：**0.14.5 修过一次（寄存时连带搬走出站队列、复活时按新世代补发），0.14.6 又补了可靠确认（Ack/Resume）以覆盖"已交给 Steam 但尚未确认"的那一段；这两个版本已按用户要求整体回滚，0.14.4 不含这些修复。** 需要时可用 `git revert 33e9956` 或直接检出 `b847113` 取回。

**规避**：尽量让干道别断（网络稳定、避免同时大流量下载、`relay` 模式）；干道断得越少，这个洞越不可能出现。

### 13.2 日志口径问题（0.14.4）

`流结束（<kind>）… 理由=…` 里的 kind/reason 是**硬编码**的：0.14.4 无法区分"游戏侧主动关闭"、"我们自己 destroy"、"干道断开导致的清理"。看到 `本机游戏服务把这条件接关了` **不能**直接认定是游戏侧的错——这正是排查时最容易走偏的地方。0.14.5 曾把 kind 扩到 15 种并附 `发起方=` 字段，随回滚一并移除。

### 13.3 未验证项

- **与真实好友的 Minecraft 联机**：未判定为"已修复"。曾有一局（0.14.5 加入者）在**没有发生迁移、没有暂停、`dropped=0`** 的稳态下仍然掉线，客户端日志显示异常抛在解码**对端发来**的字节时 ⇒ 该次故障**不是** §13.1 的迁移空洞，方向指向房主侧或更上游；需要两端同为 0.14.5+ 并做字节账本对账才能定案。
- **跨机（两台真实机器 + 两个 Steam 账号）的完整联机流程**：仅在本机自连与局域网内验证过。
- `docs/多通道选路设计.md` 描述的选路方案：**未实现**。
- `network/mux-session.cjs` 与 `steam-adapter.cjs` 内部 MUX 实现**尚未合并**（功能等价，属于技术债）。

### 14.3 术语表
