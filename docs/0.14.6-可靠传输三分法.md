# 0.14.6 可靠传输三分法：一条流的字节按"命运"分成三类

## 1. 结论

0.14.5 修掉的是"**还没交给 Steam**"的字节；0.14.6 修的是"**已经交给 Steam、但还没被对端确认**"的字节。

一条本机 TCP 流的字节，在同一时刻只有三种命运：

| 类别 | 含义 | 谁知道它的下落 | 0.14.6 之前 | 现在 |
|------|------|----------------|-------------|------|
| ① 还没交给 Steam | 还压在出站队列（`egress`）里 | 我们自己 | 干道一断随 peer 一起消失（0.14.5 已修） | `takePending()` 整段取回，随流迁移后按原顺序补发 |
| ② 交给 Steam 了、对端还没确认 | `sendMessage()` 返回成功 ≠ 对端收到 | **只有对端说得清** | **黑洞**：流照旧"原地复活"，对端收到中间缺一截的字节流 | `Resume(起点)` + 补发，接收端切掉重复前缀（既不全丢也不重复） |
| ③ 对端确认已交付 | 对端按顺序交付给了它的本机 socket | 对端的 `Ack` | 没有这个概念（`remoteCredit` 只写不读、`encodeWindow` 从没发出去过） | 累计 `Ack` 之前不许再发 |

现场三种客户端异常（`incorrect header check` / `unknown compression method` / `length wider than 21-bit`）都是同一件事的形状：**这条 TCP 字节流中间少/多了一段**，Minecraft 的 netty 解码器在包边界上错位。

## 2. 协议（`network/stream-mux.cjs`）

线上格式不变：`len:4 | type:1 | streamId:4 | generation:4 | payload`。

| 帧 | 值 | 方向 | 载荷 | 语义 |
|----|----|------|------|------|
| `Ack` | `0x08` | 接收方 → 发送方 | 4 字节 BE | "这条流我已经按顺序交付到第 X 字节"（累计值，只前进） |
| `Resume` | `0x09` | 发送方 → 接收方 | 4 字节 BE | "接下来的 DATA 从这条流第 X 字节开始"（跨世代补发前必须先发） |

- 老版本收到这两种帧只会当成"不认识的类型"忽略，不会当成协议错乱 ⇒ 版本兼容。
- 只有"确认过对端会 Ack"（收到过 `Ack`）才会发 `Resume`，所以与老版本对端互通时行为与 0.14.5 一致。

## 3. 各文件与功能（`network/steam-adapter.cjs`）

| 函数 | 功能 |
|------|------|
| `noteStreamSent(stream, chunk)` | 记下"刚交给 Steam 的原始字节"（`{offset, buf}`），累加 `sentBytes` / `sentLogBytes` |
| `trimStreamSent(stream)` | 丢掉已被确认（`end <= ackedBytes`）或超出内存上限（512 KiB）的最老记录 |
| `noteStreamAck(stream, upto)` | 确认点单调前进；迟到的旧 `Ack` 返回 0，不许倒退 |
| `resendTailFrames(stream, generation, stats, skipTailBytes)` | 生成 `Resume(起点) + DATA(补发内容)`；用 `skipTailBytes` 把①那一截刨掉，避免补两遍 |
| `pendingDataBytes(frames)` | 数出 `pendingFrames` 里"还没交给 Steam"的 DATA 字节数（就是 `skipTailBytes`） |
| `setResumeOffset(stream, offset)` | 接收端：算出要切掉多少重复字节；`offset > delivered` 时返回 `{gap}` |
| `takeDelivery(stream, payload)` | 接收端：切掉重复前缀并交付；整段重复时返回 `null` |
| `maybeAckStream(stream, peer, pushFrames)` | 交付量比上次通告多出 ≥32 KiB 时回一个累计 `Ack` |
| `createStreamAudit()` / `auditFeed()` / `auditSide()` / `auditFields()` | 流级字节账本：两个方向各记字节数 + 两个哈希 + 每 64 KiB 块指纹（`SHL_STREAM_AUDIT=0` 可关） |

| 位置 | 功能 |
|------|------|
| 房主 `writeStream()` / `socket.on('connect')` | 交付给游戏服务后累加 `delivered`，按阈值回 `Ack` |
| 房主 / 加入者流对象字面量 | 新增 `sentBytes` / `sentLog` / `sentLogBytes` / `ackedBytes` / `ackSeen` / `delivered` / `ackedSent` / `skipBytes` |
| 所有把 DATA 交给 Steam 的出口 | 一律先 `noteStreamSent()`（房主 socket data、加入者 socket data 两条分支、两处 `parkQueue` 补发） |
| `adoptOrphan()` / `resumeOrphanStreams()` | 复活顺序：`Resume + ②补发` → ①（`retagFrame` 改世代的 `pendingFrames`）→ `parkQueue` |
| 两处 `handleStreamFrame()` | 新增 `Ack` / `Resume` 分支；`Resume` 报 `gap` 时 `ERESUMEGAP` + 如实断流（不交出一条有洞的字节流） |

## 4. 实机验证

- **隧道字节完整性：已验证。** `tools/steam-integrity-probe.cjs`（同一进程里两个真实 `SessionManager`，走真实 Steam P2P + 真实本机 TCP）：64 MB 下行 + 16 MB 上行逐字节一致；注入 15% 随机拒收（12180 次发送 / 1934 次被拒绝）后 32 MB + 8 MB 仍逐字节一致。
- **与好友的真实 Minecraft 联机：尚未验证。** 需要两端都升到 0.14.6，然后在同一局里按流号比对两端 `%APPDATA%\stronghold-link\startup.log` 的 `账本=出… 入…`：
  - 全等 ⇒ 这条流经隧道一个字节没变（问题在游戏侧或对端应用）；
  - 不等 ⇒ 用 `账本块` 的块指纹定位首个不同的 64 KiB，并据此判断方向。
