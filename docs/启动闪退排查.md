# 启动闪退排查：打包后双击没反应 / 一闪就退

## 1. 结论先说

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 双击 `Stronghold Link.exe`，一闪就退、没有任何提示 | 本机 **Chromium 沙箱初始化失败**。实测：不带参数 6 秒内进程已退出，且**不会生成 startup.log**，说明死在 Electron 主进程执行 JS 之前；带 `--no-sandbox` 则 `--smoke` 返回 `ok: true`、窗口正常 | **用包里的 `点我启动-Stronghold-Link.cmd` 启动**，它默认带 `--no-sandbox` |
| 有时带参数也崩，事件日志里出现第三方模块 | **注入型软件**：Windows 事件日志显示 `Faulting module name: GPP64.dll`，游戏加加 GamePP 3.7.57；stderr 里有 `fail CreateSemaphore[5]: ... GAMEPP-IPC-OVERLAY` | 完全退出**游戏加加**；建议一并关掉 NVIDIA Overlay、Nahimic、RTSS / MSI Afterburner |

在 JS 里用 `app.commandLine.appendSwitch('no-sandbox')` **来不及**，沙箱在 JS 执行之前就已初始化。这一点是实测否定的：加了它仍然没有 startup.log、仍然秒退。所以必须由**命令行参数**传入。

## 2. 正确启动方式

1. 把整个压缩包**完整解压**到一个新文件夹。不要只复制 exe，也不要覆盖旧版本。
2. 双击 **`点我启动-Stronghold-Link.cmd`**。它会先检测注入型软件并给出提示，然后依次尝试三种启动方式：带 `--no-sandbox`；失败自动换 `--no-sandbox --disable-gpu`；再失败才试标准模式。三种方式都失败时，它会打印日志路径并暂停，不会一闪而过。
3. 首次运行还会在包内生成一个兼容模式快捷方式 `Stronghold Link（兼容模式）.lnk`。之后直接双击这个快捷方式也行。
4. 可选：把生成的快捷方式发送到桌面。

## 3. 出问题时看这两个日志

| 文件 | 内容 |
| --- | --- |
| `%APPDATA%\stronghold-link\launcher.log` | 启动器的每一次尝试与退出码，形如 `尝试1(--no-sandbox) 退出码=...` |
| `%APPDATA%\stronghold-link\startup.log` | 应用内部启动轨迹：argv、版本、`app ready`、窗口创建、渲染进程加载成功或失败、`render-process-gone`、`child-process-gone`、`gpu-process-crashed`、未捕获异常、「另一个实例已在运行」等 |

判断口径：

- **有 launcher.log、没有 startup.log** → 进程死在 Electron 主进程之前 → 沙箱问题，用启动器；或被注入 DLL 干掉，退游戏加加。
- **有 startup.log 且停在「app ready」之前** → 同上。
- **有 startup.log、停在「主窗口已创建」但没到「渲染进程加载完成」** → 渲染进程加载失败，日志里会有 `code/desc/url`。
- **正常一次的 startup.log 长这样**：
  ```
  === 启动 === version=0.9.0 ... no-sandbox=auto
  app ready
  主窗口已创建
  渲染进程加载完成
  ```

## 4. 自己动手验证，可选

```powershell
# 直接验证 exe 本体没问题，会写结果文件，不会弹窗口
& ".\Stronghold Link.exe" --smoke --no-sandbox --smoke-out="$env:TEMP\shl-smoke.json"
type "$env:TEMP\shl-smoke.json"     # 期望看到 "ok": true
```

`--smoke` 会走完「渲染进程加载 → preload 桥 → IPC → 房主会话 → 端口监听 → 加入者中继 → 数据往返 → 停止 → 端口释放」。`"ok": true` 表示程序本身完全正常，问题只在启动方式或外部注入。

## 5. 其他可能

- **SmartScreen / 杀毒拦截**：本程序未做代码签名，Windows 会提示「未知发布者」。点「更多信息 → 仍要运行」。若被杀毒直接删除，请把该文件夹加入信任列表。
- **解压不全**：只把 exe 拖出来是跑不起来的，`resources/` 等目录必须一起解压。
- **已经有一个实例在跑**：新实例会立刻退出，日志里会写「另一个实例已在运行」。打开任务管理器结束所有 `Stronghold Link` 进程后再启动。
- **想保留 Chromium 沙箱**，安全要求更高的场景：设置环境变量 `SHL_KEEP_SANDBOX=1` 再启动。应用自身的 `contextIsolation` / `nodeIntegration=false` / preload 白名单 / CSP 始终不变。

## 6. Qt 前端（`app_qml`）的同类问题：注入型软件 + 运行目录

新的 Qt Quick 前端（`StrongholdLink.exe`）会遇到**同一类**注入问题，但表现和绕法不一样，
2026-10 实测记录如下。

**现象**：进程以 `0xC0000005`（`-1073741819`）退出，一行界面都不出；Windows 事件日志

```
Faulting application name: StrongholdLink.exe
Faulting module name: GPP64.dll, version: 3.7.57.625
Exception code: 0xc0000005
```

stderr 里先刷一串

```
[E] fail CreateSemaphore[5]: _cond_sem__waiter_cond___CC_CONN__GAMEPP-IPC-OVERLAY
[E] fail CreateFileMapping[5]: __AC_CONN__GAMEPP-IPC-OVERLAY
[E] [cc_acc] acquire failed: __CA_CONN__
```

即游戏加加（GamePP）的覆盖层 DLL 已注入进进程，但它拿不到自己的 IPC 命名对象
（`ACCESS_DENIED`），随后在进程里崩掉。**同一个二进制换目录就能跑**，这是关键线索：

| exe 所在目录 | 结果 |
| --- | --- |
| 仓库里（`…\source\app_qml\build\release\release\`、`…\source\app_qml\_locI\`） | 每次必崩 |
| `%TEMP%\shl-H\`、`%TEMP%\stronghold-link\`、`%TEMP%\shl-run\`、`D:\shl\qmlrun\` | 正常出图 |
| 改名（`shlprobe.exe`）、换渲染后端（`QT_QUICK_BACKEND=software`）、关掉流动背景层 | 仍然崩（都不是原因） |

**解决**：

1. **首选**：完全退出游戏加加（托盘右键退出，确认任务管理器里没有 `GamePP.exe`）。
2. **不能退它时**：把 exe 复制到一个仓库之外的目录再启动（比如 `D:\shl\qmlrun\`），
   后端脚本用环境变量指回仓库里的真脚本，行为完全一致：

   ```powershell
   $env:SHL_BACKEND_SCRIPT = "<仓库>\backend\stronghold-backend.cjs"
   & "D:\shl\qmlrun\StrongholdLink.exe"
   ```

   仓库自带的 `tools/make-shots.cjs` 已经内置了这个绕法（先复制到 `%TEMP%\shl-shots`
   或 `--runDir` 指定的目录再跑）。建议一并关掉 NVIDIA Overlay、Nahimic、RTSS / MSI Afterburner。

**为什么值得单独记一笔**：这个坑会伪装成"我们的程序崩了"—— 事件日志里进程名是自己的、
报错在启动几秒内、而且换个目录就好，很容易误判成路径相关的代码 bug（当时确实按这个方向
排查了一轮：改进程名、换渲染后端、逐层关界面、`git stash` 回到上一个提交，全都照崩）。
判断口径：**事件日志里的出错模块不是自己的 DLL（`GPP64.dll` / `Nahimic*` / `RTSS*` 之类）
就是注入问题，先退掉那些工具再谈代码。**

## 7. 另一类"闪退"：退出码 `0xC0000135`（缺 Qt 运行库）

Qt 前端是动态链接的，`StrongholdLink.exe` 启动时要去 `PATH` 里找
`Qt6Core.dll` / `Qt6Gui.dll` / `Qt6Qml.dll` / `Qt6Quick.dll` 以及 MinGW 运行库。
**找不到时它会在 1 秒内静默退出，退出码 `3221225781`（`0xC0000135`），
`stdout` / `stderr` 一个字都不写，也不生成 `startup.log`** —— 从外面看就是"什么都没发生"。

判断口径：**看退出码。`0xC0000135` = 缺运行库；`0xC0000005` = 注入（见第 6 节）。**
两者都会表现为"一闪就退"，但处理方式完全不同。

解决：把这两个目录加进 `PATH`（本机 Qt 6.8.3 的安装位置）：

```powershell
$env:PATH = "D:\Qt\6.8.3\mingw_64\bin;D:\Qt\Tools\mingw1310_64\bin;$env:PATH"
```

`tools/make-shots.cjs` 会自己拼好这两个目录；用 `D:\shl\tools\app-memory-probe.cjs`
做内存验收时**必须自己先设 `PATH`**，否则探针会报"抓不到任何进程、窗口核对 no-window"，
而这个现象和注入崩溃长得一模一样（探针现在会在启动 2 秒内退出时直接打印退出码与结论）。
