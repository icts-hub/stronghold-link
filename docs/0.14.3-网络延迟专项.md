# 0.14.3 网络延迟专项 · 三阶段报告

**状态：Phase 1、Phase 2 已完成，全量测试 766 / 765 通过 / 0 失败 / 1 跳过。Phase 3 拿到了真机读数并写出了限速模型 —— 但真机（环回）压不出调度差异，能证明的只有"它不是瓶颈"，量到差异的那条证据线是模型。**

**行号说明**：本文里的 `文件:行号` 按撰写时的快照写，改动后可能位移，以函数名/常量名为准。

## 0. 三句话结论

1. **本机链路上 MUX 从来不是瓶颈**：收包与分发 0.01ms 量级、服务处理 0.03ms 量级、干道吞吐 **421MB/s**、出站队列在每一个 1Hz 采样点都是 **0 字节**。所以"卡不卡"在本机测不出来。
2. **"地图一动人就飘"的形态是出站队列不公平**：0.14.2 把所有帧塞进同一条 FIFO，一张 900KB 的地图区块能把一个 64 字节的移动包挡住 **1556ms（p95）/ 1736ms（max）**（限速模型实测，512KB/s 链路）。这正是拥塞链路上的症状，环回 400MB/s 永远复现不出来。
3. 0.14.3 改成**每流一条队列 + 流间轮转（quantum 4096）**，同一场景降到 **0ms（p50/p95/max，模型分辨率即一个 4ms 回调节拍）**；一条环境变量可整块退回 0.14.2 的老调度。

### 2.3 顺手修掉的四个"量错"（不修的话后面所有读数都是假的）

| # | 症状 | 真因 | 修法 |
| --- | --- | --- | --- |
| 1 | `resolutionMs` 恒为 `null` | Node 24 上 `IntervalHistogram.resolution` 是 `undefined` ⇒ `undefined/1e6` = NaN ⇒ JSON null | 固定 `LOOP_RESOLUTION_MS = 10` 作为配置值上报，并给出 15.6ms 地板说明 |

| 3 | 加入者 `serve` 永远是 0 | `recordServe` 埋在老路径 `bindLocalSocket`（只有 `mux:false` 才走），干道建好后真正跑的是 `bindStream` 的 `socket.on('data')` | 在该回调顶部取 `hrNow()`，并在**四个出口**各记一次 |

## 3. Phase 2 · 出站公平队列

### 3.1 0.14.2 的发送路径长什么样

`network/steam-adapter.cjs`：

- 所有帧（地图区块、玩家移动、OPEN/CLOSE、会话帧、魔数）都进**同一条扁平数组** `peer.out`，先到先发；
- `queueOut()` 每被调一次就把整个数组求和一遍（O(n)），只为判断要不要立刻 flush；
- `flushPeerOut()` 把整个队列 `Buffer.concat` 成一条 payload 交给 `sendChunk`，成功就整队清空、失败就整队留下重试。

后果：一条 64 字节的移动包，只要排在 900KB 的地图区块后面，就得等这 900KB 全部进 Steam 发送缓冲。

### 3.2 新模块 `network/egress-queue.cjs`

| 能力 | 做法 |
| --- | --- |
| 分流 | 干道队列（魔数、`streamId=0` 的会话帧）一条 + **每条流一条** FIFO |
| 调度 | 干道整段在最前，然后**流间轮转**，每个回合每条流最多 `quantum`（默认 4096）字节 |
| 顺序 | **流内严格 FIFO** ⇒ OPEN→DATA→CLOSE 不可能乱序（同一流的帧永远同一条队列） |
| 出队 | 只在**确认进了 Steam 缓冲之后**出队，且只出**被确认的前缀**（跨队列也对） |
| 计数 | `total()` **现算**（不是缓存），背压判据不会因为漏减而永久 pause |
| 诊断 | `queueRows()` 报每条队列的字节数、最老那批字节等了多久、段数 |

导出：`{ DEFAULT_FAIR_QUANTUM: 4096, TRUNK_KEY: 'trunk', enqueue, prepend, total, oldestAt, resync, dropTrunk, planOut, commit, clear, queueRows }`。

### 3.3 接进活路径（`network/steam-adapter.cjs`）

| 位置 | 改动 |
| --- | --- |
| `queueOut()` | 改成 `egress.enqueue(peer, chunk, key)`，删掉每次调用的 O(n) 求和 |
| `frameOutKey(frame)`（新增） | 从帧头第 5 字节读 `streamId`（帧头格式 `\|len:4\|type:1\|streamId:4\|gen:4\|payload\|`，见 `network/stream-mux.cjs`）；魔数 / 流号 0 / 长度异常的进干道 |
| 两个 `pushFrames()`（房主、加入者） | 都传 `fairKey(frame, tuning)` —— 二十多个调用点一个都没改，靠帧头解析 |
| `flushPeerOut()` | `planOut` → `Buffer.concat(计划段)` → `sendChunk` → 只 `commit` 被确认的前缀；失败仍然整队留下 + 背压 |
| `peerOutBytes()` | 改成 `egress.total(peer)`（现算）；`flushPeerOutSoon` / `drainThenClose` / `retryUndecidedTrunks` 全部改用它 |
| `schedulePeerReconnect()` / 旧版重连补发 | `egress.clear()` / `egress.prepend()`（插到干道队头） |
| 诊断构造 ×2 | 新增 `peerOutQueues` ⇒ 每个 1Hz 帧里带 `egressQueues`（每条流排了多少、最老等了多久） |

## 4. ★ 限速模型抓到的缺陷（Phase 2 自己引入、又被模型抓住的那一个）

真机环回 421MB/s、队列永不积压 ⇒ **公平调度在真机上量不出差异**。于是我写了限速模型（`tools/steam-egress-sim.cjs`）把链路压到 512KB/s ~ 5MB/s，让真实的 `egress-queue.cjs` 在里面跑。

**第一次跑就现形**：512KB/s、quantum 4096 时，小包的等待是 **p95 1556ms / max 1736ms**，而设计意图是"最多等一个量子 ≈ 8ms"（同一次跑里 quantum 512 却是 0ms ⇒ 不是"量子太大"这么简单）。

**真因**：`planOut()` 每次 flush 都**从 Map 里第一条流重新开始轮转**。而一次 flush 被 Steam 接受的字节数**经常小于一个 quantum** —— 512KB/s ÷ 4ms 节拍 = 2048 字节 < 4096。于是计划的第一段永远属于那条大响应的流，排在后面的流**无限期饿死**；量子越小，第一条流越快让位，所以 512 反而"看起来正常"。

> 这就是"地图一动人就飘"在拥塞链路上的形态：越拥塞越饿死，而本地环回永远不会拥塞。

**修法**：轮转起点**跨 flush 记住**（`peer.outCursorKey` = 上一次计划里第一条流），下一次计划从**它的下一条流**开始；`ensure()` 初始化、`clear()` 归零。修完同一场景 p50/p95/max 全是 **0ms**。

**回归用例**：`test/egress-queue.test.cjs` 里 `★ 拥塞链路回归：一次 flush 吃不满一个 quantum 时，轮转起点要跨调用往前走 —— 后面的流不许被饿死`（连续 8 轮、每轮只确认 1 字节，断言小包所在流必须在前两轮拿到机会）+ `★ clear 之后轮转游标要归零`。

## 5. Phase 3 · 真机对照与限速模型

### 5.1 真机 A/B（公平开 / 关各 3 轮，20s/轮，6 条测量连接 @200ms + 4 条 bulk 256KB/20ms）

| 轮次 | appRtt p50 | p95 | max | 回显完整 | bulk 吞吐 |
| --- | --- | --- | --- | --- | --- |
| flat r1 / r2 / r3 | 12 / 13 / 10 | 45 / 54 / 47 | 55 / 109 / 53 | 588/588、588/588、594/594 | 46.2 / 45.6 / 46.4 MB/s |
| fair r1 / r2 / r3 | 11 / 13 / 15 | 60 / 66 / **258** | 76 / 78 / **438** | 588/588、588/588、564/564 | 45.3 / 44.6 / 39.1 MB/s |

**结论（如实写）**：**两种调度在这条环回链路上无法区分**，全部差异落在噪声带内（fair r3 的 p95 258ms 是事件循环/调度抖动，同一跑法里 flat 也出现过 max 109ms；bulk 吞吐 39.1~48.7MB/s 的波动同理）。原因见 5.2，不是"公平调度没用"。

### 5.2 为什么真机量不出来

- 环回链路的干道吞吐是 **421MB/s** 量级（8 条 bulk 连接打满时 `steamConnections[0].outBytesPerSec = 421,161,312`，而 `bytesBuffered/queueMs/pendingReliable` 全是 0）⇒ **出站队列从头到尾没有积压，公平调度没有可调度对象**。
- 想把真机干道限速到"朋友家上行"，**这个绑定做不到**：`steamworks-ffi-node` 只暴露**只读**的 `m_nSendRateBytesPerSecond`（`node_modules/steamworks-ffi-node/dist/internal/SteamNetworkingSocketsManager.js:748` 的注释：`// int m_nSendRateBytesPerSecond; // offset 32, 4 bytes`）与枚举 `ESteamNetworkingConfigValue.SendRateMin = 10`（`dist/types/networking.js:115`），**没有任何 `SetConfigValue` 包装**（全仓库 grep 无命中）。

### 5.3 限速模型（0.14.2 老调度 vs 0.14.3 公平调度）

模型设定：900KB 大响应在 t=0 一次性到齐、64 字节小包每 20ms 一个（50Hz）、回调节拍 4ms、每节拍预算 = 速率 × 4ms（等价 Steam 发送缓冲）、只确认被接受的前缀；度量 = 小包**最后一个字节**被交出去的时刻。**模型里没有 Steam / SDR 拥塞控制 / 丢包重传 / 事件循环开销**。

| 限速 | 模式 | 小包 p50 | p95 | max | 大响应完成 | 计划段/节拍 |
| --- | --- | --- | --- | --- | --- | --- |
| 512KB/s | 老（0.14.2） | 0 | **1556** | **1736** | 1756ms | 41.63 |
| 512KB/s | 公平 q=512 | 0 | 0 | 0 | 1768ms | 725.57 |
| 512KB/s | 公平 q=4096 | 0 | 0 | 0 | 1768ms | 96.57 |
| 512KB/s | 公平 q=16384 | 0 | 0 | 0 | 1768ms | 29.19 |
| 1024KB/s | 老 | 0 | 676 | 856 | 876ms | 17.99 |
| 1024KB/s | 公平 q=512 / 4096 / 16384 | 0 | 0 | 0 | 880ms | 533.92 / 71.29 / 21.73 |
| 2048KB/s | 老 | 0 | 236 | 416 | 436ms | 7.88 |
| 2048KB/s | 公平 q=512 / 4096 / 16384 | 0 | 0 | 0 | 440ms | 349.61 / 46.98 / 14.56 |
| 5120KB/s | 老 | 0 | 0 | 152 | 172ms | 3.15 |
| 5120KB/s | 公平 q=512 / 4096 / 16384 | 0 | 0 | 0 | 172ms | 173.92 / 23.81 / 7.73 |

结论：

- **老调度在 512KB/s 上把移动包挡了 1.5 秒** —— 这就是现场症状的量化形态；链路越快挡得越短（5MB/s 时 max 152ms），与"我们俩都还行、他那条上行慢"的现场一致。
- **公平调度把等待压到一个回调节拍以内**（模型分辨率 4ms，测出来 0ms），代价只是把 payload 切成更多段。
- **量子只影响段数（CPU），不影响等待**（因为轮转起点跨 flush 记住了）；`q=4096 → 96.57 段/节拍`，`q=16384 → 29.19`。

## 6. 参数与调优建议

| 参数 | 建议 | 依据 |
| --- | --- | --- |
| `SHL_STEAM_FAIR_QUEUE` | 保持开 | §5.3 |
| `SHL_STEAM_FAIR_QUANTUM` | 保持 4096 | 512KB/s 上 4096 的等待已经是一个节拍内；8192/16384 能把段数再降 2~3 倍，但**只有真机出现 CPU 瓶颈时才值得动**，而本机事件循环 p99 28ms 与队列无关 |
| `SHL_STEAM_MAX_CHUNK` | **未做真机扫描**（保持 4096） | 环回的噪声带（p95 45~258ms）比这个参数的影响大，扫了也不可信；要扫必须在真跨机链路或受限速模型上做 |
| `SHL_STEAM_CALLBACK_MS` | **未改**（保持 4） | 同上；另外注释里已实测 Windows 上 `setInterval(4)` 实际 14.3ms、`setInterval(16)` 实际 25.0ms |
